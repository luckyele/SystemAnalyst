## 二、知识点：统一过程-UP特征与四阶段提交结果

### 1. 核心原理
统一过程（UP/RUP）是**用例驱动、以架构为中心、受控的迭代式增量开发**过程。其时间结构是三层嵌套：**一个 UP 分为若干个周期（Cycle）→ 每个周期分 4 个阶段（Phase）→ 每个阶段内可做若干次迭代（Iteration）**。命题最密集的锚点是**各阶段的意图与提交结果（Deliverables）**：

| 阶段 | 主要意图 | 提交结果 |
| --- | --- | --- |
| **初始阶段**（Inception） | 建立**项目的范围和版本**，确定**业务实现的可能性**和**项目目标的稳定性** | **原始的项目需求** + **业务用例** |
| **精化阶段**（Elaboration） | **对问题域进行分析**，建立**系统的需求和架构**，确定**技术实现的可行性**和**系统架构的稳定性** | **系统架构及其相关文档** + **领域模型** + **修改后的业务用例** + **整个项目的开发计划** |
| **构建阶段**（Construction） | **增量式地开发**一个**可以交付用户的软件产品** | 可交付用户的软件产品（增量） |
| **提交阶段**（Transition） | **将软件产品提交用户** | 交付到用户手中的产品 |

一句话记忆：**初始定范围出用例，精化出架构加计划，构建增量造产品，提交交给用户家**。

### 2. 关键公式/规则

| 名称 | 内容 |
| --- | --- |
| UP 三大基本特征 | 用例驱动、以架构为中心、受控的迭代式增量开发 |
| 三层时间结构 | UP → 周期（Cycle）→ 阶段（Phase）→ 迭代（Iteration，阶段内若干次） |
| 四阶段顺序 | 初始（Inception）→ 精化（Elaboration）→ 构建（Construction）→ 提交（Transition） |
| 初始提交结果锚点 | 原始项目需求、业务用例 |
| 精化提交结果锚点 | 系统架构及相关文档、领域模型、修改后的业务用例、开发计划 |
| 构建意图锚点 | 增量式开发、可交付用户的软件产品 |
| 提交意图锚点 | 将软件产品提交用户 |
| 译名等价 | 精化 = 细化（Elaboration）；提交 = 移交 = 交付（Transition） |

### 3. 解题步骤
1. 先认结构层级：题干问"UP 的基本特征"→ 背三特征；问"周期/阶段/迭代关系"→ 三层嵌套；问"某产物属于哪个阶段"→ 提交结果归位。
2. 提交结果归位按关键词：
   - "原始的项目需求 / 业务用例" → **初始**；
   - "系统架构 / 领域模型 / 开发计划 / 修改后的业务用例" → **精化**；
   - "增量式开发 / 可交付用户的软件产品" → **构建**；
   - "将产品提交用户" → **提交**。
3. 遇到译名差异（精化/细化、提交/移交/交付）先换算成英文再对号，不要当成不同阶段。

## 三、易错点
1. **译名漂移是最常见陷阱**：本图用"精化/提交"，教程另一版本用"细化/移交（交付）"。Elaboration 精化=细化，Transition 提交=移交=交付；选项换译名不代表换了阶段。
2. **"开发计划"归精化不归初始**：整个项目的开发计划是**精化阶段**的提交结果，别因"计划听起来像开局"而误归初始阶段。
3. **"领域模型"归精化不归初始**：初始阶段只出**原始项目需求和业务用例**；领域模型是精化阶段分析问题域的产物。
4. **"修改后的业务用例"在精化**：初始出的是**原始**业务用例，精化阶段**修改**后再次提交——两个阶段都有"业务用例"，区别在原始 vs 修改后。
5. **构建阶段的意图是"增量式开发"**：关键词是"增量"+"可交付用户的软件产品"，别与提交阶段"将产品提交用户"混淆——构建造出来，提交交出去。
6. **UP 特征别说漏"受控"**：完整表述是"用例驱动、以架构为中心的**受控的**迭代式增量开发"；漏"受控"或写成"无反馈的"都是错误选项。
7. **周期 ≠ 阶段**：一个 UP 分若干**周期**，每个周期才分 4 个**阶段**，阶段内还有若干**迭代**；三层不可混。
