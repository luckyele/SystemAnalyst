
# 备考笔记：架构风格-黑板风格与管道过滤器

## 一、题目

> （ ）架构风格的特点是共享数据区，谁感兴趣谁处理；管道-过滤器风格的核心是（ ）。
>
> A. 黑板风格，数据流式处理
> B. 过程调用，数据流式处理
> C. 共享内存，数据流式处理
> D. 消息传递，共享内存

**答案：A. 黑板风格，数据流式处理**

解析：第一空的关键词是"**共享数据区**""**谁感兴趣谁处理**"——这正是**仓库（Repository）/黑板风格**的典型描述：多个**知识源**围绕一块**共享数据区（黑板）**工作，**没有构件间的直接调用**，谁需要数据谁读、谁有能力处理谁写。第二空问**管道-过滤器风格的核心**：数据从**管道**流入**过滤器**，逐个加工、流水传递，即**数据流式处理**。故选 **A**。

## 二、知识点：架构风格-黑板风格与管道过滤器

### 1. 核心原理

**软件架构风格 = 构件 + 连接件 + 约束**。按构件交互方式可分为五大类，本题考其中的两种：

- **仓库风格（Repository）**：以**中心数据结构**为核心，其余构件围绕它读写。
  - **数据库系统**：中心是**数据库**，构件是**应用程序**；
  - **黑板（Blackboard）**：中心是**共享数据区（黑板）**，构件是**知识源（独立处理单元）**；
  - **超文本系统**：中心是**超文本链接结构**。
  - **特征**：数据**集中共享**；构件**不直接通信**，只与中心数据结构交互；**谁感兴趣谁处理**（机会主义求解），**控制权可转移**（哪个知识源适用就由它接管）。
- **数据流风格**：数据按**确定的顺序**流动并被逐步加工。
  - **批处理序列**：整体批量处理，前后步之间是**完整数据**；
  - **管道-过滤器（Pipe-Filter）**：数据以**流**的方式经过一串**过滤器**，**管道**负责传递。

**黑板风格典型应用**：**人工智能、信号处理、语音/图像识别、编译器词法-语法-语义分析**——这类问题**没有确定的解法路径**，需多来源知识协同、逐步逼近。

**管道-过滤器典型应用**：**编译器的各阶段、批处理数据转换、Unix 命令管道（`cat | grep | sort`）、ETL 数据处理**。

### 2. 关键公式/规则

**五大类架构风格速查表**（高频考点）：

| 大类 | 典型风格 | 连接件/核心机制 | 一句话特征 |
| --- | --- | --- | --- |
| **数据流** | 批处理序列、**管道-过滤器** | 数据流（管道） | **数据流式处理**，顺序加工 |
| **调用/返回** | 主程序-子程序、**面向对象**、**层次结构** | 调用/返回 | 过程调用，自顶向下 |
| **独立构件** | **进程通信**、**事件驱动（隐式调用）** | 消息/事件 | 消息传递、发布-订阅 |
| **虚拟机** | **解释器**、**规则系统** | 状态机/规则解释 | 用软件模拟"机器" |
| **仓库** | **数据库、黑板、超文本** | 中心数据结构 | **共享数据区，谁感兴趣谁处理** |

**四种风格的核心对照**：

| 风格 | 核心连接机制 | 记忆锚点 |
| --- | --- | --- |
| **黑板** | **共享数据区** | "**共享数据，谁懂谁上**" |
| **管道-过滤器** | **数据流** | "**数据流式处理**" |
| **过程调用** | 调用/返回 | "**自上而下调用**" |
| **消息传递** | 消息/事件 | "**发消息、松耦合**" |

**黑板与管道-过滤器的本质区别**：

| 对比项 | 黑板风格 | 管道-过滤器 |
| --- | --- | --- |
| 数据组织 | **中心共享数据区** | **无中心，逐个流过滤波器** |
| 控制流 | **无预定顺序，谁感兴趣谁处理** | **顺序确定，逐步加工** |
| 构件耦合 | 通过黑板**间接交互** | 通过管道**串接** |
| 可复用性 | 知识源可独立替换 | **过滤器独立、可组合复用** |
| 适用问题 | 无确定解法的复杂问题（AI/识别） | 数据转换/批处理/流水线 |

### 3. 解题步骤

1. **抓题眼**：第一空"**共享数据区 + 谁感兴趣谁处理**"→ 直接锁定**仓库类风格**（黑板/数据库）；再看"谁感兴趣谁处理"强调**多个主动知识源**，即为**黑板**。
2. **排除干扰**：B"过程调用"是调用/返回风格；C"共享内存"不是标准架构风格名称（是**实现手段**，非风格）；D"消息传递"是独立构件风格——均不符"共享数据区"的规范表述。
3. **第二空**：管道-过滤器 = **数据流式处理**，A/C 的第二空都对，但 C 第一空错，故选 **A**。

## 三、易错点

1. **"共享数据区"误选"共享内存"**：架构风格的标准名称是**仓库/黑板风格**，"共享内存"是**操作系统层面的实现技术**，不是风格名——C 就靠这个词形接近来设陷。
2. **把"谁感兴趣谁处理"当事件驱动**：**事件驱动（隐式调用）**是"发布事件、订阅者响应"，连接件是**事件/消息**；而**黑板**的连接件是**共享数据区**。区别在**是否存在中心数据结构**。
3. **管道-过滤器 vs 批处理序列**：两者都属**数据流风格**；**批处理序列**各步处理完整数据、不并行，**管道-过滤器**数据以**流**传递、过滤器可**并发**。第二空若问"数据流式处理"，两者都算，重点看第一空的风格名。
4. **忘了"过滤器"是独立构件**：管道-过滤器**不共享状态**（无全局数据），每个过滤器只依赖输入、产出输出，所以**可复用、可重组**——这是它的最大优点，也是与黑板的根本差异。
5. **黑板只有"共享"没有"控制"**：黑板的关键除了**共享数据区**，还有**知识源机会主义调度、控制权转移**——正因为**没有预定算法**，才需要"谁感兴趣谁处理"。
6. **数据库风格与黑板混淆**：两者都属**仓库风格**，区别在于——**数据库**是被动存储、由外部程序主动查询；**黑板**由**知识源主动触发**，是"活的共享区"。

## 四、扩展延伸

- **黑板风格的经典案例**：**HEARSAY-II 语音识别系统**——多个知识源（声学、句法、语义）共享一块黑板，逐层补充假设，谁有把握处理谁上，最终由不同来源的知识拼出整句识别结果。这类问题**无确定解法**，故不能写成固定流水线。
- **管道-过滤器的工程影响**：
  1. **可复用**：过滤器是"输入→输出"的纯函数式构件，可跨系统拼装（Unix 管道哲学）；
  2. **可并发**：过滤器间通过管道缓冲，天然支持流水线并行；
  3. **代价**：**不适合交互式应用**（数据流是单向的），且**过滤器间无共享状态**，复杂决策难表达。
- **架构风格与质量属性的对应**（常连考）：

| 质量属性 | 更受益的风格 |
| --- | --- |
| **可修改性/可复用性** | 管道-过滤器、层次结构、隐式调用 |
| **可扩展性** | 事件驱动（隐式调用）、微内核 |
| **性能** | 层次结构（层间开销）较差；管道-过滤器较好 |
| **可测试性** | 管道-过滤器（过滤器可独立测） |
| **处理无确定解法问题** | **黑板** |
- **现实类比**：
  - **黑板风格**＝**一群人围着白板解题**：谁有想法谁上去写，别人看了接着补，没人指挥顺序，最后拼出答案；
  - **管道-过滤器**＝**流水线装配**：原料从管道流入，每个工位（过滤器）只管自己那道工序，做完交给下一个；
  - 一句话：**黑板是"围着白板群策群力"，管道是"排队流水线各干一小步"**。
