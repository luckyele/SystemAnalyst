# 备考笔记：微服务架构组件-API网关与服务注册发现

## 一、题目
> 试题五（25分）·问题2（8分）
>
> 某传统零售企业将原单体销售系统改造为微服务架构，拆分为用户服务、商品服务、订单服务、库存服务 4 个微服务，引入 **API 网关**作为统一入口，采用 **服务注册与发现**组件管理各个服务实例，同时引入配置中心。试运行期间出现：订单/库存跨服务事务不一致、日志分散难排查、调用链路过长难以定位故障等问题。
>
> (1) 案例中 **API 网关**在微服务架构中有哪些主要作用？写出 3 点。
> (2) **服务注册与发现**组件的主要功能是什么？

**答案要点：**
- (1) API 网关主要作用：①**统一接入与路由转发**（所有客户端请求经网关路由到对应微服务）；②**统一鉴权与安全管控**（集中身份认证、权限校验、签名验签、防爬防刷）；③**流量治理与协议适配**（限流、熔断、降级、负载均衡、协议转换 / 请求聚合），可再补充监控日志、灰度发布、缓存加速等。
- (2) 服务注册与发现组件主要功能：①**服务注册**（服务实例启动时向注册中心登记网络地址、端口、元数据）；②**服务发现**（服务消费者从注册中心查询可用实例列表并缓存订阅）；③**健康检查与上下线通知**（定期探测实例状态，自动剔除不健康实例并通知订阅方），可再补充负载均衡策略选择、服务分组 / 版本 / 区域路由。

## 二、知识点：API 网关与服务注册发现

### 1. 核心原理

**API 网关（API Gateway）** 是微服务架构中**所有外部请求的统一入口**，位于客户端与内部微服务之间，承担"门面（Facade）"角色。它把客户端原本需要直接感知多个微服务地址、协议、鉴权方式的复杂性，**收敛到网关一层**集中处理，让客户端像调用单个服务一样使用整个系统。

**服务注册与发现（Service Registry & Discovery）** 是微服务**动态寻址**的"通讯录 + 健康中心"。服务实例**启动时**把自身网络信息（IP、端口、实例 ID、元数据）写入**注册中心**；调用方**消费时**从注册中心**查询**可用实例并**订阅**其变化；当实例**上下线 / 故障**时，注册中心主动通知订阅方，实现"实例位置透明 + 故障自动剔除"。

### 2. 关键对比与公式

#### 2.1 API 网关主要作用清单（任答 3 点）

| 序号 | 作用 | 说明 |
| --- | --- | --- |
| 1 | **统一入口 / 路由转发** | 所有客户端请求统一经此进入，按 URL / Header / 路径匹配转发到对应微服务 |
| 2 | **统一鉴权 / 安全管控** | 集中身份认证、令牌签发、权限校验、防爬防刷、防 SQL 注入 |
| 3 | **流量治理（限流 / 熔断 / 降级）** | 按 IP / 用户 / API 维度限流，熔断异常服务，降级返回兜底数据 |
| 4 | **负载均衡** | 客户端负载或服务端负载，把请求分发到多实例 |
| 5 | **协议转换 / 请求聚合** | 适配 HTTP / HTTPS / WebSocket / gRPC，聚合多个微服务调用为一次响应 |
| 6 | **监控日志 / 链路追踪接入点** | 统一埋点、生成 traceId、聚合访问日志 |
| 7 | **灰度发布 / 蓝绿发布** | 按用户 / 版本号路由到不同实例组 |
| 8 | **缓存加速** | 对热点数据做网关级缓存，减轻下游压力 |

#### 2.2 服务注册与发现主要功能清单

| 序号 | 功能 | 说明 |
| --- | --- | --- |
| 1 | **服务注册** | 实例启动时向注册中心登记 IP、端口、服务名、版本、元数据 |
| 2 | **服务发现（订阅）** | 消费者启动时拉取 / 订阅服务列表，缓存到本地 |
| 3 | **健康检查** | 心跳 / TCP / HTTP 探测，自动剔除不健康实例 |
| 4 | **变更通知** | 实例上下线时主动通知订阅方，本地缓存实时更新 |
| 5 | **负载均衡策略** | 随机、轮询、最小连接、一致性 Hash 等（部分实现） |
| 6 | **元数据 / 分组 / 区域管理** | 多版本、多机房、灰度分组路由 |

> 答题口诀：**API 网关**记"**入口 + 鉴权 + 限流**"三件套；**服务注册发现**记"**注册 + 发现 + 健康检查**"三件套。

#### 2.3 常见实现组件对比

| 组件类别 | 常见实现 | 备注 |
| --- | --- | --- |
| API 网关 | Spring Cloud Gateway、Zuul、Kong、APISIX、NGINX + Lua、Envoy | 部署在边缘 |
| 注册中心 | Eureka（AP）、Consul（CP）、Nacos（AP/CP 可切）、Zookeeper（CP） | 选型参考 **CAP 理论** |

### 3. 解题步骤

1. **看分值定条数**：本题 8 分、第 (1) 问"写出 3 点"，必须**至少答满 3 点**，每点 1 行，**多写不扣分**。
2. **API 网关按"入口 / 安全 / 治理"维度展开**：不要只答"路由转发"一条，要覆盖**接入 + 鉴权 + 限流熔断 / 聚合 / 监控**中至少 3 类。
3. **服务注册发现按"注册 + 发现 + 健康 + 通知"四步流程答**：体现**动态寻址 + 故障自愈**两个核心价值。
4. **联系案例中的故障**：可适当引"日志分散 / 调用链路过长"对应"网关聚合监控、注册中心健康检查 + 配合链路追踪组件"作为加分项。
5. **格式工整**：用"① ② ③"或"1. 2. 3."分点，避免一长段不分层。

## 四、易错点

1. **把 API 网关答成"路由器"或"防火墙"**：API 网关是**业务级**的统一接入层，处理鉴权/聚合/限流等业务规则；与硬件路由器（网络层）、Web 应用防火墙 WAF（安全层）侧重点不同。
2. **漏答"鉴权 / 限流 / 熔断"任一项**：本题偏好答"**统一鉴权 + 流量治理**"，仅答路由转发会被认为覆盖不全。
3. **把服务注册发现答成"配置中心"**：注册中心管的是**实例地址 + 状态**，配置中心管的是**配置参数**，案例中已分别引入，不要混淆。
4. **漏答"健康检查"**：健康检查是服务注册发现**区别于 DNS** 的关键点——DNS 只做静态域名解析，注册中心能**主动剔除故障实例**，必须答出。
5. **忘写"通知订阅方 / 本地缓存更新"**：仅答"注册 + 发现"会被认为不完整，应答出"**变更通知**"这一动态机制。
6. **没联系题干痛点**：题干提到"日志分散、调用链路过长难定位"，可在答案里点出"统一日志接入点 / 统一 traceId 入口"作为加分。

## 五、扩展延伸

- **与配套组件的协作**：
  - **配置中心**（Nacos/Apollo）：管配置参数，与注册中心解耦但常部署在同一组件中（如 Nacos 同时支持注册 + 配置）。
  - **分布式链路追踪**（Sleuth + Zipkin / SkyWalking）：解决"调用链路过长难定位"——网关生成全局 `traceId`，各微服务传递 `spanId`。
  - **集中日志系统**（ELK / Loki）：解决"日志分散"——网关或 Sidecar 收集日志统一入库。
  - **熔断限流**（Sentinel / Resilience4j）：常与网关协同，或作为网关插件。
- **数据一致性**：题干中"订单已生成但库存未扣减"对应**分布式事务问题**，可用 **Saga（补偿事务）**、**TCC**、**可靠消息最终一致性**等方案，与本题 API 网关 / 注册发现并列，但属于另一类考点。
- **CAP 取舍**：注册中心选型本质是 **AP vs CP** 权衡——Eureka 偏 AP（可用性优先、故障时仍可访问旧列表）；Consul/Zookeeper 偏 CP（强一致、故障时拒绝写）。
- **与现有笔记的联系**：
  - [32-微服务系统特征.md](32-微服务系统特征.md)：本笔记是其"配套基础设施"层；32 讲特征，本笔记讲落地组件。
  - [16-分布式数据库-CAP理论.md](16-分布式数据库-CAP理论.md)：注册中心选型直接套用 CAP 框架。
  - [80-SOA-ESB总线分层与职责.md](80-SOA-ESB总线分层与职责.md)：API 网关 vs ESB 的角色对比——网关**轻量、边缘、专注接入**，ESB**重量、中心、含编排**。
- **现实类比**：API 网关像**写字楼前台 + 安保**——所有访客（请求）必经前台（统一入口），前台分配楼层（路由）、核对工牌（鉴权）、管控人流（限流）；注册中心像**大楼通讯录 + 门禁系统**——员工入职（注册）登记工位，通讯录实时更新，离职（健康检查失败）即从通讯录消失。
