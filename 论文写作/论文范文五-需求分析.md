# 论文范文五：论信息系统需求分析及应用（系统分析师真题）

> 本篇为图传真题「试题四」的成文，与《论文范文四-需求管理》共用同一项目。分工：范文四答「需求管理」专题题（理论主轴：基线/变更/跟踪/评审三形式），本篇答「需求工程五环节全景」题（理论主轴：获取/分析/定义/验证/管理）。写作方法按《如何让论文逻辑更清晰》执行。

## 题目

论信息系统需求分析及应用。信息系统需求分析是开发过程中的关键阶段，通过对用户业务目标、业务流程以及功能需求进行调查、分析和整理，形成系统建设的需求基础。科学有效的需求分析方法能够降低系统建设风险，提高系统开发质量。请围绕"论信息系统需求分析及应用"论题，依次从以下三个方面进行论述：

1. 简述你参与建设的信息系统项目，以及在项目中承担的主要工作；
2. 从需求获取、需求分析、需求定义、需求验证和需求管理等方面，论述你是如何开展信息系统需求工程的整体工作的；
3. 结合具体项目说明在整个需求工程过程中遇到的问题和解决方案。

## 摘要（约400字）

2024年3月，某省属大型制造集团启动智能供应链协同平台建设，旨在打通ERP、MES、WMS等既有系统，实现订单、库存、物流的线上化协同。项目投入约1200万元，团队32人，周期14个月，拆分微服务60余个，接入供应商800余家，日均处理订单12万单，两地三中心部署。建设初期需求问题突出：业务部门需求变更月均40余次，需求返工一度占开发工作量约三成。我作为系统分析师，主持项目需求工程全过程，负责干系人分析、业务流程建模、需求规格定义与需求基线管理。我按需求获取、需求分析、需求定义、需求验证、需求管理五个环节组织需求工作：多渠道交叉获取原始需求300余项；以流程建模、用例建模完成需求分析与冲突消解；以条目化规格与需求跟踪矩阵落实需求定义；以原型确认与三级评审完成需求验证；以基线冻结与变更控制实现需求受控管理。最终需求变更返工率下降约35%，项目按14个月周期按期上线并通过验收。本文结合该项目论述需求工程的整体开展过程，并分析遇到的问题与解决方案。

## 正文

### 一、项目概述与承担的工作（约420字）

2024年3月，我所在团队承接了某省属大型制造集团智能供应链协同平台建设项目。集团原有ERP、MES、WMS等系统烟囱林立，订单协同依靠人工Excel传递，供应商询价、对账、异常处理均在线下完成，管理层要求打通产供销数据、实现供应链全流程线上化协同。

项目投入约1200万元，团队32人跨5个业务域并行开发，周期14个月，采用微服务与云原生架构，拆分微服务60余个，纳管容器实例约900个，接入供应商800余家，目标日均处理订单12万单，两地三中心部署。由于需求质量直接决定60余个微服务的边界划分、800余家供应商的协同规则以及后续验收依据，我们把需求工程作为项目的第一道质量关口。

我作为系统分析师，主持需求工程全过程：第一，负责干系人识别与分析，制定需求获取计划；第二，主导业务流程梳理与用例建模，完成需求分析与确认；第三，主持需求规格说明书编写与需求基线确立；第四，组织需求评审与验证；第五，负责需求变更的受控管理。本文从需求获取、需求分析、需求定义、需求验证和需求管理五个方面论述需求工程的整体开展过程，并说明遇到的问题与解决方案。

### 二、需求工程的整体开展过程（约1400字）

**（一）需求获取方面。** 需求获取的关键是多渠道交叉印证，防止单一来源的需求失真。首先我运用干系人分析，识别出集团销售、供应商、仓储物流、财务结算四类核心干系人，按影响力与关注点制定差异化获取策略。具体做法上：对集团内部业务骨干开展结构化访谈23场；面向地域分散的800余家供应商发放线上问卷，回收有效问卷612份；同时带领两名分析师驻仓储现场跟岗两周，记录拣货、发货、对账的真实作业过程，并收集历史订单与异常单据样本1100余份。由于内部管理诉求靠访谈、供应商痛点靠问卷、一线作业真相靠观察，三类来源交叉比对后共形成原始需求300余项，为后续分析提供了全面且真实的素材底座。

**（二）需求分析方面。** 需求分析的核心是从杂乱的原始诉求中提炼出结构化、无矛盾的需求模型。我采用流程建模、用例建模、数据建模三位一体的方法：用BPMN绘制订单协同、供应商对账、异常处理等核心业务流程38个，明确每个环节的岗位、输入输出与异常分支；用UML用例图识别参与者与系统交互，整理用例120余个；对订单、库存等核心实体建立领域模型，明确实体关系与关键属性。分析中同步界定非功能需求，明确下单接口P99响应不超过500毫秒、系统可用性不低于99.95%等可度量指标，避免非功能需求事后补课。分析阶段还承担冲突消解职能，销售与财务在下单审核环节的激烈分歧，正是通过流程建模量化后组织工作坊解决的（详见第三部分问题二）。

**（三）需求定义方面。** 需求定义的目标是形成准确、一致、可验证的需求规格说明书。我按需求条目化原则编写SRS：把300余项原始需求按业务需求、用户需求、系统需求三层组织，细化后的1200余条需求条目逐条赋予唯一编号，注明来源、优先级与验收准则；同时建立需求跟踪矩阵，把系统需求与设计模块、测试用例逐层映射，保证每条需求向上可追溯至业务目标、向下可落实到测试用例。条目化与跟踪矩阵让"每条需求可验证、每段实现有出处"，为后续变更影响分析与验收测试提供了基准依据。

**（四）需求验证方面。** 需求验证既要检查"文档写得对不对"，更要确认"这就是不是用户要的"，我的思路是让确认活动前移到编码之前而不是等到验收。第一，原型先行：制作核心业务页面高保真原型42个，组织供应商代表与内部用户逐页确认，提前暴露交互层面的理解偏差；第二，三级评审：重大需求规格走项目组内审、跨部门会审、集团专家终审，累计发现并修正需求缺陷87项；第三，验收准则可测试：凡验收准则不可度量的一律退回重写。通过验证前移，大量需求缺陷在编码开始前即被拦截，显著降低了后期返工成本。

**（五）需求管理方面。** 需求管理的要义是基线受控、变更有序、全程可追溯。需求经终审后即冻结为需求基线并纳入配置管理；所有变更统一走"申请—影响分析—变更控制委员会（CCB）审批—实施—回归验证"流程，CCB按双周例会运转，紧急变更走快速通道但须事后追认；影响分析从工期、成本、质量三个维度评估波及范围，例如一次订单分配规则变更经影响分析发现波及12个微服务、3个测试域，CCB据此把变更拆成两期实施，避免了带病上线。同时借助需求跟踪矩阵做双向核对：前向检查每条需求是否有实现载体，反向检查新增代码是否挂靠需求，需求遗漏与超范围实现被同时堵住，整个建设周期的需求变更始终处于受控状态。

### 三、需求工程中遇到的问题及解决方案（约780字）

**问题一：供应商干系人分散，需求获取覆盖不足。** 项目启动前两周，集中访谈仅覆盖12家头部供应商，问卷回收率不足三成，获取的需求存在明显样本偏差，中小供应商的痛点大量缺失。分析根因：供应商地域分散、信息化水平参差不齐，且对配合调研缺乏动力。为此我调整获取策略：把问卷嵌入供应商入驻注册流程并压缩至10分钟内完成，辅以电话回访；遴选6家有代表性的中小供应商驻场观摩其作业过程；联合集团采购部门把调研配合纳入供应商准入加分项。调整后问卷回收率提升到76%，新增中小企业侧需求40余项，其中对账自动匹配需求后来成为平台的亮点功能。

**问题二：部门间需求冲突僵持不下。** 需求分析阶段，销售与财务就下单审核环节的分歧持续三周无法收敛：销售坚持三步完成下单，财务坚持七步逐单风控，双方各执一词。我判断根因在于两部门考核目标不同，单纯协调立场没有出路，于是把"立场之争"引导为"数据之争"：分别按两种方案建模测算，三步方案下单提效但差错单处理成本高，七步方案风险可控但大促期间会造成订单积压。在数据基础上组织联合工作坊，最终形成按订单金额分级审核的方案：小额订单系统自动审核秒级通过，大额订单双人复核。上线后平均审核环节压缩至2.4步，风控合规与作业效率同时得到满足，两个部门均接受该方案。

**问题三：开发中期需求变更一度失控。** 进入开发中期，业务部门变更申请月均40余次，部分变更直接打乱迭代计划，需求返工一度占开发工作量约三成。复盘根因有二：一是基线确认停留在部门负责人层面，一线操作人员到开发后期才提出实际作业障碍；二是变更提交零门槛，缺乏影响分析约束。为此我双管齐下：一方面建立双周需求澄清会，邀请一线跟单员对照原型逐场景确认，把障碍消灭在变更发生之前；另一方面严格执行变更控制流程，变更申请必须附三维度影响分析，杜绝随意变更。机制运转三个月后，需求变更返工率从约28%降到18%，交付准时率提升到92%，开发节奏恢复稳定。

### 四、总结与展望（约140字）

2025年5月，项目一期按期上线并通过验收，订单协同全流程线上化，日均处理订单12万单，系统运行稳定。实践证明，结构化的需求工程方法能有效降低建设风险、提高开发质量：条目化需求与跟踪矩阵支撑了验收一次通过，基线与变更控制让返工大幅下降。不足在于需求获取对一线用户的覆盖仍依赖人工组织，后续我计划建设需求资产库沉淀历史需求，并探索利用大模型辅助需求一致性检查与变更影响归因，持续提升需求工程的质量与效率。

## 范文自评对照（评分五维）

- **切合题意（30%）**：三问严格分段作答，第一段只做项目与职责铺垫，第二段按题干关键词"获取、分析、定义、验证、管理"分五节作答，第三段专论问题与解决，理论不进第一段、项目细节不挤占理论段，题干三个要点全部覆盖。
- **应用深度与水平（20%）**：五节各给一条方法论主旨（交叉印证、三位一体建模、条目化+追溯、验证前移、基线受控），非功能需求、需求跟踪矩阵、验证与确认之辨等专业元素自然嵌入，理论成体系而非罗列。
- **实践性（20%）**：五节均有具体做法与数字（23场访谈、612份问卷、38个流程、1200余条条目、42个原型、87项缺陷），三个问题按"现象带数字→根因→措施→量化效果"闭环展开。
- **表达能力（15%）**：全文以我为中心叙述，术语首尾统一（需求跟踪矩阵、需求基线、变更控制委员会CCB），每段首句即主旨句，列举用"第一/第二/第三"，段落短小。
- **综合与分析能力（15%）**：问题按项目时间递进（获取期→分析期→开发期），冲突处理体现"立场之争转数据之争"的分析方法，结尾直面一线覆盖不足并给出需求资产库与大模型辅助的改进方向。

## 《如何让论文逻辑更清晰》方法落点对照

| 文中方法 | 论文中的落点 |
|---|---|
| 骨架先行，小问一一对应 | 一/二/三段分别对应三问，四为总结；摘要承诺"五个方面"=第二部分正好五节 |
| 小节标题直接抄题目关键词 | （一）至（五）原样使用题干"需求获取/需求分析/需求定义/需求验证/需求管理" |
| 点题→思路→做法→效果 | 每小节首句点题，次句给思路，中间两三句做法，末句收效果 |
| 逻辑连接词显式化 | 首先/由于/为此/一方面另一方面/正是通过/最终贯穿全文 |
| 问题四步闭环 + 排序逻辑 | 三个问题均为现象带数字→根因→措施→量化效果，按获取期→分析期→开发期时间排序 |
| 一段一事，主旨句先行 | 每段首句即主旨句；段内列举显式编号 |
| 前后呼应 | 结尾回扣摘要的"按期上线、12万单、返工下降"；（二）节冲突案例与第三部分问题二显式互指 |
