# 案例题骨架：微服务改造案例（试题五·问题1 8分 + 问题2 8分 + 问题3 9分）

体例参照 [论文骨架四篇.md](file:///home/lucky/备考笔记/论文写作/论文骨架四篇.md)：先还原题干与考点，再给「元素全集 + 区分性表述 + 易混对照 + 失分提醒 + 可直接默写句式」。案例题按点给分，故本骨架的核心是「每问写满可抓分的点」，而非概念堆砌。

## 一、题目还原与考点定位

### 题干摘要

某传统零售企业把原有单体线上销售系统（用户、商品、订单、库存、支付对接）改造为微服务：拆为用户服务、商品服务、订单服务、库存服务 4 个独立微服务，引入 API 网关统一入口、注册发现组件管理实例、配置中心统一配置。改造后开发独立、部署独立、迭代加快，但试运行阶段暴露三个问题：

1. 一次下单需调用订单服务与库存服务，二者各操作自己的数据库；订单创建成功而库存扣减失败，出现「订单已生成、库存未扣减」的数据不一致。
2. 各微服务产生大量日志，日志分散在不同服务器，故障排查困难。
3. 部分服务调用链路过长，一个业务请求跨多个微服务，出问题时难以定位是哪个服务出错。

### 试卷结构与骨架分布（本题 25 分）

| 题号 | 分值 | 问法 | 本骨架位置 |
| --- | --- | --- | --- |
| 问题1 | 8 分 | 简述微服务架构的主要优点，结合本案例写出 4 点 | 第二节 |
| 问题2 | 8 分 | (1) API 网关的主要作用写 3 点；(2) 服务注册与发现组件的主要功能 | 第三节 |
| 问题3 | 9 分 | 针对试运行阶段的 3 个问题给出对应解决方案 | 第四至六节 |

### 考点定位

| 题号 / 问题 | 核心考点 | 高频关键词 |
| --- | --- | --- |
| 问题1 微服务优点 | 单体与微服务对比、架构风格特征 | 独立部署、故障隔离、技术异构、团队自治、弹性伸缩 |
| 问题2-① API 网关 | 网关职责与服务治理 | 统一入口、路由转发、鉴权限流、协议适配、灰度分流、日志监控 |
| 问题2-② 注册与发现 | 服务治理基础设施 | 服务注册、心跳续约、健康检查、实例摘除、变更推送、本地缓存 |
| 问题3-① 数据不一致 | 分布式事务与数据一致性 | CAP/BASE、Saga、TCC、可靠消息最终一致、幂等、补偿、对账 |
| 问题3-② 日志分散 | 日志集中管理与可观测性 | ELK/EFK、Filebeat/Fluentd、Kafka 缓冲、结构化日志、分级采样 |
| 问题3-③ 定位困难 | 分布式链路追踪 | SkyWalking/Jaeger、TraceId+SpanId、调用拓扑、三支柱联动定位 |

### 答题总原则

- 问题1 是「按点给分」题：8 分 = 4 点 × 每点 2 分，写 3 点即失 2 分，写满 4 点即止，不追加第 5 点挤占时间。
- 问题1 每点必须「优点名称 + 本案例事实印证」两句话，凡只写通用优点不结合案例，按半分计。
- 问题2-① 三点须落在不同维度（入口路由、安全管控、流量治理/协议适配），同维度重复按一点计；问题2-② 按「注册—发现—健康检查—变更通知」四环节写全。
- 问题3 每条按「定性 → 方案 → 落地 → 兜底」四句式写，约 120 至 150 字，三小问篇幅均衡（9 分约每问 3 分，偏科即失分）。
- 先点方案名称（给阅卷人抓分点），再写怎么落地（得分深度），最后补一句兜底或边界（拿综合分析分）。
- 问题1、2、3 合计 25 分，建议问题1 用 8 分钟、问题2 用 8 分钟、问题3 用 10 分钟，均不恋战。

## 二、【问题1】微服务架构的主要优点（8分）

### 命题拆解

- 8 分 = 4 点 × 每点 2 分，题干已限死「写出 4 点」，写 3 点必失 2 分，写 5 点不加分。
- 「结合本案例」是硬要求：每点写成「优点名称 + 案例事实印证」两句话，只写通用优点按半分计。
- 最省力且最不易漏点的结构：把题干里单体的 4 条痛点**逐条反转**成微服务的 4 条优点，一一对应。

### 答题骨架（4 点，按题干痛点顺序排布）

| 单体痛点（题干原句） | 反转后的优点（得分点） | 案例印证写法 |
| --- | --- | --- |
| 每次小功能修改都要整体重新部署整个系统 | ① 独立部署、独立发布，变更影响面小 | 商品服务调整价格规则只需单独发布该服务，不必停整站，发布频率由每月一次提升到每周一次 |
| 某模块出现性能问题会拖慢整个系统 | ② 故障隔离与独立弹性伸缩 | 大促仅对订单、库存服务横向扩容，单服务性能瓶颈或故障不再拖慢用户、商品服务 |
| 全部模块只能用统一技术栈，部分业务想选更合适技术无法实现 | ③ 技术异构、按业务选型自由 | 订单、库存等高并发服务用 Go 实现，管理类服务保留 Java Spring Cloud，接口契约不变 |
| 团队变大后多组协同修改同一套代码，冲突频繁、效率下降 | ④ 按业务边界拆分、团队自治、代码库独立 | 四个服务对应四个业务域、四个小组各自维护独立仓库，经 API 网关联调，协同冲突消除 |

### 备用第 5 点（不占 4 点名额，仅在写完 4 点有余力时补一句）

- 服务可复用、易集成：用户、商品服务以标准 REST 接口对小程序、门店 POS 等多渠道复用，新增渠道不改核心逻辑。

### 答题句式（每点约 40 字，两点一句亦可）

- 「微服务按业务能力拆分为独立部署单元，本案例商品服务修改后只需单独发布、无需整体重启，变更影响面显著缩小。」
- 「服务间以接口隔离，故障不扩散：本案例大促期间仅对订单与库存服务扩容，单服务性能问题不再拖慢整个系统。」
- 「各服务可按需选择技术栈：本案例订单、库存等高并发服务采用 Go，其余保留 Java 技术栈，对外接口契约保持一致。」
- 「按业务边界划分服务与团队，四个小组各自维护独立代码库，从根本上消除了多人协同修改同一份代码的冲突。」

### 失分提醒

- 只写「高内聚低耦合、易扩展、易维护」等空泛词而不落到案例，8 分通常只拿 3 至 4 分。
- 把缺点当优点写（如「分布式事务简单」「运维成本低」），方向性错误，整点不得分。
- 四点互相重叠（「独立部署」与「独立发布」拆成两点），按一点计。
- 漏掉题干明示的两条痛点对应项：技术栈异构、团队协同效率，是最常见的漏点。

## 三、【问题2】API 网关作用与服务注册发现（8分）

### 命题拆解

- 8 分拆两小问：(1) 写 3 点，约 5 分（每点 1.5 至 2 分）；(2) 功能写全，约 3 分。
- (1) 三点必须落在不同维度——入口路由、安全管控、流量治理（或协议适配、日志监控），同义反复只按一点计。
- (2) 问「主要功能」，标准答案是四件事：注册、发现、健康检查、变更通知（摘除）。

### (1) API 网关的主要作用（写 3 点，每点一句展开）

| 作用 | 一句展开 |
| --- | --- |
| ① 统一入口与路由转发 | 对外只暴露一个域名，按路径或服务名把请求转发到用户、商品、订单、库存服务，客户端不必感知实例地址与拆分变化 |
| ② 统一安全与访问控制 | 集中做身份认证、Token 校验、权限控制、限流防刷、黑白名单、SSL 卸载，各服务不再重复实现 |
| ③ 流量治理与灰度发布 | 按权重或标签分流实现灰度与 A/B，配合负载均衡、重试、熔断，故障服务可快速摘除 |
| ④ 协议适配与响应聚合（后备） | 完成 HTTP 与内部 RPC 协议转换，一次请求聚合多个服务结果并裁剪冗余字段 |
| ⑤ 统一日志与监控（后备） | 集中记录访问日志与响应时长，在入口注入 TraceId，贯通全链路追踪 |

- 写法：优先写 ①②③ 三条（入口、安全、治理），④⑤ 作为备用，三点写满即止。

### (2) 服务注册与发现组件的主要功能

1. 服务注册：实例启动时向注册中心登记服务名、IP、端口、版本与元数据。
2. 心跳续约与健康检查：实例定期心跳续约，注册中心结合主动探测判定实例是否健康。
3. 服务发现：消费方按服务名查询可用实例列表，结果缓存在本地，避免每次调用都访问注册中心。
4. 变更推送与实例摘除：实例上下线时推送变更，客户端刷新缓存，故障实例自动摘除、不再接流量。
5. 配合负载均衡：向调用方或服务端负载均衡器提供实例列表，完成请求分发。
6. 延伸一句（可选）：Nacos 等组件还兼具配置管理能力，与本案例配置中心对应。

### 答题句式

- (1)：「一是统一入口与路由转发，客户端只访问网关域名，由网关转发到四个微服务；二是统一认证鉴权与限流防刷，避免各服务重复实现安全逻辑；三是灰度分流与协议适配，按权重分流上线新版本，并完成协议转换与响应聚合。」
- (2)：「注册与发现组件完成四件事：实例启动时注册自身地址与元数据，定期心跳并由注册中心做健康检查，消费方按服务名发现可用实例并本地缓存，实例上下线时推送变更、自动摘除故障节点，从而使服务地址变化对调用方透明。」

### 失分提醒

- (1) 三点同质：把「路由转发、反向代理、请求分发」当三点写，只按一点计分。
- (1) 职责混淆：把「服务注册与发现」写进网关作用，或把网关写成单纯的负载均衡器。
- (2) 只答「注册」与「发现」两个词，漏健康检查与变更推送，通常只给一半分。
- 通篇不结合案例：网关作为统一入口、注册发现管理 4 个服务实例，是题干明示事实，须至少点到一处。

## 四、【问题3-①】分布式数据一致性（3分）

### 第一句定性

本质是跨服务、跨数据库的分布式事务问题。微服务架构下不宜采用强一致的 2PC/XA（同步阻塞、协调者单点、可用性差），应按 BASE 原则走「最终一致 + 补偿」。

### 方案层（写出 2 至 3 个，标明适用场景）

1. Saga（主答方案）：把下单拆成「订单服务创建订单」与「库存服务扣减库存」两个本地事务，每个正向操作配一个补偿动作；库存扣减失败即触发补偿——将订单置为已取消或待退款，释放已占资源。分协同式（事件驱动、服务间互相监听）与编排式（中心协调器统一调度）两种形态。
2. 可靠消息最终一致：本地消息表或 RocketMQ 事务消息，订单库本地事务与「扣减库存消息」同库落盘，保证「订单落库则消息必达」；库存服务消费成功才确认，失败重试。
3. TCC（资源预留型场景）：Try 阶段预占库存、Confirm 阶段确认扣减、Cancel 阶段释放预占，适合库存这类需要锁定资源的业务，改造侵入较大。
4. Seata AT 模式：注解式全局事务，改造成本低，适合改造初期快速接入。

- 反向点一句（体现取舍）：两阶段提交仅适合单应用内多数据源，跨微服务不推荐。

### 落地细节（最容易丢分的得分点）

- 幂等：以业务唯一流水号 + 去重表/状态机保证重复消费不重复扣减。
- 重试与死信：失败重试设上限，超限进死信队列并告警，转人工介入。
- 兜底对账：日终跑「订单—库存」对账任务，自动识别并修复差异数据。
- 业务降级：库存服务不可用时，下单转「预占/挂起」状态，不直接报错丢单。

## 五、【问题3-②】日志集中管理（3分）

### 第一句定性

日志分散在各服务器与容器内，属于可观测性缺失，需建设「采集 → 传输 → 存储 → 检索 → 展示」的集中式日志链路。

### 方案层

1. 采集层：Filebeat/Fluentd 轻量采集；容器化环境以 DaemonSet 采集标准输出，随 Pod 生命周期自动发现新实例。
2. 缓冲层：Kafka 削峰解耦，避免日志洪峰打垮存储与检索。
3. 存储检索层：Elasticsearch 建索引 + Kibana 多维检索与看板；规模较小时可用 Loki 降低存储成本。
4. 规范层（最能拉开差距，务必写）：统一 JSON 结构化日志，统一字段（timestamp、serviceName、level、traceId、host），统一时区与日志级别口径。
5. 治理层：日志分级与采样、冷热分层（热数据留 ES，冷数据转对象存储）、保留周期策略、敏感信息脱敏。

### 收尾联动一句

日志中强制打印 TraceId，才能与问题3-③的链路追踪打通，实现「链路定位到服务、日志定位到异常」。

## 六、【问题3-③】链路追踪与故障定位（3分）

### 第一句定性

调用链路拉长后，故障定位从「单机看日志」变为「跨服务看路径」，需要全链路追踪与指标、日志三者联动。

### 方案层

1. 链路追踪：选 SkyWalking（Java Agent 无侵入探针，对 Spring Cloud 生态友好）或 Zipkin/Jaeger；TraceId 由网关统一生成，经 HTTP Header、RPC 上下文透传，各服务以 SpanId 记录分段耗时，自动生成服务依赖拓扑与耗时瀑布图，直接定位到最慢或报错的 Span 及其所属服务。
2. 指标监控：Prometheus + Grafana，为每个服务打 RED 指标（Rate、Error、Duration），先由指标发现异常服务。
3. 三支柱联合定位（答题亮点）：指标定「哪个服务异常」→ 链路追踪定「哪个 Span 异常」→ 日志看「具体异常堆栈」，形成三级下钻。
4. 服务网格旁路：Istio 侧车代理上报调用数据，业务代码零改造即可获得调用指标与拓扑。
5. 稳定性配套：Sentinel/Resilience4j 做熔断、降级、限流，防止单点故障沿长链路雪崩；架构上以异步化、接口聚合、减少同步调用层级来缩短链路。

## 七、易混对照表（防「说了但说错」）

| 易混点            | 区分口径                                        |
| -------------- | ------------------------------------------- |
| 微服务 vs 单体    | 按业务能力拆分、独立部署、独立数据存储 vs 单进程内模块化、统一部署单元       |
| 微服务 vs SOA    | 去中心化治理、轻量协议、服务自治 vs 以 ESB 为中心的重量级服务编排与共享总线  |
| 微服务优点 vs 微服务挑战 | 独立部署、故障隔离、技术异构、团队自治 vs 分布式事务、运维复杂、链路难追踪（即本案例试运行三问题） |
| API 网关 vs 服务网格（Istio） | 南北向流量：对外统一入口、鉴权、路由与灰度 vs 东西向流量：Sidecar 旁路治理服务间调用、熔断与观测 |
| 注册中心 vs 配置中心 | 存服务实例地址与健康状态、支撑调用寻址 vs 存应用配置并动态推送（Nacos 二者兼有） |
| 服务注册 vs 服务发现 | 提供方写入自身实例信息 vs 消费方按服务名读取可用实例列表并缓存          |
| 2PC/XA vs Saga | 强一致、同步阻塞 vs 最终一致、逐步补偿                       |
| Saga vs TCC    | 每步本地事务 + 反向补偿 vs Try/Confirm/Cancel 三阶段资源预留 |
| 可靠消息 vs 最大努力通知 | 保证消息必达并重试消费 vs 尽力通知、不保证到达                   |
| 幂等 vs 重试       | 重试的前提保障 vs 失败后的再执行动作                        |
| ELK vs EFK     | Logstash 侧重解析转换且较重 vs Fluentd/Filebeat 轻量采集 |
| 日志 vs 链路追踪     | 单服务离散事件明细 vs 跨服务一次请求的完整路径与耗时                |
| 链路追踪 vs 指标监控   | 单次请求的微观路径 vs 集群整体的宏观水位趋势                    |

## 八、常见失分点提醒

- 问题1 只背通用优点、不结合案例：8 分题「结合本案例」是独立采分点，脱离四个微服务、网关、注册中心等事实即降档。
- 问题1 点数不足或凑数：8 分四点各 2 分，写 3 点直接扣 2 分；把「独立部署」与「独立发布」拆成两点凑数，按一点计。
- 问题1 把微服务缺点或实现手段当优点：写「分布式事务由 Saga 解决」「容器化部署」属答非所问。
- 问题2-① 三点同质：把「统一入口、路由转发、请求分发」拆成三点，只按一点计。
- 问题2-① 职责越界：把服务注册发现、配置管理写进网关作用，或把网关等同于普通负载均衡器。

## 九、可直接默写的答题句式

**问题1（4 点，约 160 字）**：一是独立部署、独立发布，商品服务调整规则只需单独发布该服务，无需整体重启；二是故障隔离与独立伸缩，大促仅扩容订单与库存服务，单服务性能问题不再拖慢全局；三是技术异构，订单、库存等高并发服务采用 Go，其余保留 Java，接口契约不变；四是团队自治，四个业务域各由独立小组维护独立代码库，消除协同改代码的冲突。

**问题2-(1)（3 点，约 110 字）**：一是统一入口与路由转发，客户端只访问网关域名，由网关把请求转发到用户、商品、订单、库存四个服务，实例地址与拆分变化对客户端透明；二是统一安全与访问控制，在入口集中完成认证鉴权、Token 校验、限流防刷与黑白名单，避免各服务重复实现；三是流量治理与灰度发布，按权重或标签分流实现灰度与 A/B，并配合负载均衡、重试与熔断，故障服务可快速摘除。

**问题2-(2)（约 100 字）**：服务注册与发现组件承担四件事：实例启动时注册服务名、IP、端口与元数据；定期心跳并由注册中心做主动健康检查；消费方按服务名发现可用实例并本地缓存，避免每次调用都访问注册中心；实例上下线时推送变更、自动摘除故障节点，从而使服务地址变化对调用方透明。

**问题3-①**：该问题的本质是跨服务、跨数据库的分布式事务。微服务下强一致方案（2PC）存在同步阻塞与协调者单点问题，故采用基于 Saga 的最终一致性方案：订单服务在本地事务中创建订单并发布扣减库存事件，库存服务消费后执行本地扣减，扣减失败则由补偿逻辑将订单置为取消并释放资源；同时以业务流水号保证幂等、以日终对账兜底，确保数据最终一致。

**问题3-②**：针对日志分散，建设集中式日志平台：各节点用 Filebeat 采集、Kafka 缓冲削峰、Elasticsearch 存储、Kibana 检索与看板；同时统一结构化日志规范，强制输出 traceId、服务名、级别等字段，并实施分级采样、冷热分层与脱敏，兼顾排查效率与存储成本。

**问题3-③**：针对链路过长难定位，引入 SkyWalking 全链路追踪：网关生成 TraceId 并随请求头透传，各服务以无侵入探针上报 Span，形成调用拓扑与耗时瀑布图；配合 Prometheus 指标先定位异常服务、链路追踪定位异常 Span、集中日志查看异常堆栈，实现三级联动定位；并以熔断降级防止故障沿链路扩散。
