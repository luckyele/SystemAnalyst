## 一、题目还原与考点定位

### b题干摘要

某传统零售企业把原有单体线上销售系统（用户、商品、订单、库存、支付对接）改造为微服务：拆为用户服务、商品服务、订单服务、库存服务 4 个独立微服务，引入 API 网关统一入口、注册发现组件管理实例、配置中心统一配置。改造后开发独立、部署独立、迭代加快，但试运行阶段暴露三个问题：

1. 一次下单需调用订单服务与库存服务，二者各操作自己的数据库；订单创建成功而库存扣减失败，出现「订单已生成、库存未扣减」的数据不一致。
2. 各微服务产生大量日志，日志分散在不同服务器，故障排查困难。
3. 部分服务调用链路过长，一个业务请求跨多个微服务，出问题时难以定位是哪个服务出错。

### 考点定位（三问对应三块硬知识）

| 问题        | 核心考点        | 高频关键词                                         |
| --------- | ----------- | --------------------------------------------- |
| 问题1 数据不一致 | 分布式事务与数据一致性 | CAP/BASE、Saga、TCC、可靠消息最终一致、幂等、补偿、对账           |
| 问题2 日志分散  | 日志集中管理与可观测性 | ELK/EFK、Filebeat/Fluentd、Kafka 缓冲、结构化日志、分级采样  |
| 问题3 定位困难  | 分布式链路追踪     | SkyWalking/Jaeger、TraceId+SpanId、调用拓扑、三支柱联动定位 |

### 答题总原则

- 每条按「定性 → 方案 → 落地 → 兜底」四句式写，约 120 至 150 字，三问篇幅均衡（9 分约每问 3 分，偏科即失分）。
- 先点方案名称（给阅卷人抓分点），再写怎么落地（得分深度），最后补一句兜底或边界（拿综合分析分）。
- 建议用时 8 至 10 分钟，每问 3 分钟，不恋战。

## 二、问题1骨架：分布式数据一致性（3分）

### 第一句定性

本质是跨服务、跨数据库的分布式事务问题。微服务架构下不宜采用强一致的 2PC/XA（同步阻塞、协调者单点、可用性差），应按 BASE 原则走「最终一致 + 补偿」。

### 方案层（写出 2 至 3 个，标明适用场景）

1. Saga（主答方案）：把下单拆成「订单服务创建订单」与「库存服务扣减库存」两个本地事务，每个正向操作配一个补偿动作；库存扣减失败即触发补偿——将订单置为已取消或待退款，释放已占资源。分协同式（事件驱动、服务间互相监听）与编排式（中心协调器统一调度）两种形态。
2. 可靠消息最终一致：本地消息表或 RocketMQ 事务消息，订单库本地事务与「扣减库存消息」同库落盘，保证「订单落库则消息必达」；库存服务消费成功才确认，失败重试。
3. TCC（资源预留型场景）：Try 阶段预占库存、Confirm 阶段确认扣减、Cancel 阶段释放预占，适合库存这类需要锁定资源的业务，改造侵入较大。
4. Seata AT 模式：注解式全局事务，改造成本低，适合改造初期快速接入。

- 反向点一句（体现取舍）：两阶段提交仅适合单应用内多数据源，跨微服务不推荐。

### 落地细节（最容易丢分的得分点）

- 幂等：以业务唯一流水号 + 去重表/状态机保证重复消费不重复扣减。
- 重试与死信：失败重试设上限，超限进死信队列并告警，转人工介入。
- 兜底对账：日终跑「订单—库存」对账任务，自动识别并修复差异数据。
- 业务降级：库存服务不可用时，下单转「预占/挂起」状态，不直接报错丢单。

## 三、问题2骨架：日志集中管理（3分）

### 第一句定性

日志分散在各服务器与容器内，属于可观测性缺失，需建设「采集 → 传输 → 存储 → 检索 → 展示」的集中式日志链路。

### 方案层

1. 采集层：Filebeat/Fluentd 轻量采集；容器化环境以 DaemonSet 采集标准输出，随 Pod 生命周期自动发现新实例。
2. 缓冲层：Kafka 削峰解耦，避免日志洪峰打垮存储与检索。
3. 存储检索层：Elasticsearch 建索引 + Kibana 多维检索与看板；规模较小时可用 Loki 降低存储成本。
4. 规范层（最能拉开差距，务必写）：统一 JSON 结构化日志，统一字段（timestamp、serviceName、level、traceId、host），统一时区与日志级别口径。
5. 治理层：日志分级与采样、冷热分层（热数据留 ES，冷数据转对象存储）、保留周期策略、敏感信息脱敏。

### 收尾联动一句

日志中强制打印 TraceId，才能与问题3的链路追踪打通，实现「链路定位到服务、日志定位到异常」。

## 四、问题3骨架：链路追踪与故障定位（3分）

### 第一句定性

调用链路拉长后，故障定位从「单机看日志」变为「跨服务看路径」，需要全链路追踪与指标、日志三者联动。

### 方案层

1. 链路追踪：选 SkyWalking（Java Agent 无侵入探针，对 Spring Cloud 生态友好）或 Zipkin/Jaeger；TraceId 由网关统一生成，经 HTTP Header、RPC 上下文透传，各服务以 SpanId 记录分段耗时，自动生成服务依赖拓扑与耗时瀑布图，直接定位到最慢或报错的 Span 及其所属服务。
2. 指标监控：Prometheus + Grafana，为每个服务打 RED 指标（Rate、Error、Duration），先由指标发现异常服务。
3. 三支柱联合定位（答题亮点）：指标定「哪个服务异常」→ 链路追踪定「哪个 Span 异常」→ 日志看「具体异常堆栈」，形成三级下钻。
4. 服务网格旁路：Istio 侧车代理上报调用数据，业务代码零改造即可获得调用指标与拓扑。
5. 稳定性配套：Sentinel/Resilience4j 做熔断、降级、限流，防止单点故障沿长链路雪崩；架构上以异步化、接口聚合、减少同步调用层级来缩短链路。

## 五、易混对照表（防「说了但说错」）

| 易混点            | 区分口径                                        |
| -------------- | ------------------------------------------- |
| 2PC/XA vs Saga | 强一致、同步阻塞 vs 最终一致、逐步补偿                       |
| Saga vs TCC    | 每步本地事务 + 反向补偿 vs Try/Confirm/Cancel 三阶段资源预留 |
| 可靠消息 vs 最大努力通知 | 保证消息必达并重试消费 vs 尽力通知、不保证到达                   |
| 幂等 vs 重试       | 重试的前提保障 vs 失败后的再执行动作                        |
| ELK vs EFK     | Logstash 侧重解析转换且较重 vs Fluentd/Filebeat 轻量采集 |
| 日志 vs 链路追踪     | 单服务离散事件明细 vs 跨服务一次请求的完整路径与耗时                |
| 链路追踪 vs 指标监控   | 单次请求的微观路径 vs 集群整体的宏观水位趋势                    |

## 六、常见失分点提醒

- 只答方案名不答落地：写「采用 Saga」「采用 ELK」而无具体动作，按点给分时拿不到分。
- 问题1 主答 2PC：方向保守，未体现微服务下 BASE 取舍，综合分析分受损；且漏幂等、漏对账，视为方案不闭环。
- 问题1 只说「失败重试」：重试不解决已产生的不一致，必须有补偿或对账兜底。
- 问题2 只写 ELK 三件套：漏日志规范（结构化字段、TraceId）与治理（分级采样、冷热分层），深度不足。
- 问题3 只写「上 SkyWalking」：不写 TraceId 透传机制、不写三支柱联动，无法回答「怎么定位」。
- 三问体例不一：一问写产品名、一问写设计模式，阅卷人难对点抓分。
- 术语混用：链路追踪 / 调用链跟踪 / 全链路监控混写，表达分受损。

## 七、可直接默写的答题句式

**问题1**：该问题的本质是跨服务、跨数据库的分布式事务。微服务下强一致方案（2PC）存在同步阻塞与协调者单点问题，故采用基于 Saga 的最终一致性方案：订单服务在本地事务中创建订单并发布扣减库存事件，库存服务消费后执行本地扣减，扣减失败则由补偿逻辑将订单置为取消并释放资源；同时以业务流水号保证幂等、以日终对账兜底，确保数据最终一致。

**问题2**：针对日志分散，建设集中式日志平台：各节点用 Filebeat 采集、Kafka 缓冲削峰、Elasticsearch 存储、Kibana 检索与看板；同时统一结构化日志规范，强制输出 traceId、服务名、级别等字段，并实施分级采样、冷热分层与脱敏，兼顾排查效率与存储成本。

**问题3**：针对链路过长难定位，引入 SkyWalking 全链路追踪：网关生成 TraceId 并随请求头透传，各服务以无侵入探针上报 Span，形成调用拓扑与耗时瀑布图；配合 Prometheus 指标先定位异常服务、链路追踪定位异常 Span、集中日志查看异常堆栈，实现三级联动定位；并以熔断降级防止故障沿链路扩散。
