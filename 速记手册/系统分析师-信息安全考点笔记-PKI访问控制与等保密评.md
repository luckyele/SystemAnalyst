## 一、PKI 与数字证书体系

### 1.1 PKI 的定义与组成

**PKI（Public Key Infrastructure，公钥基础设施）**：利用**公钥密码技术**建立的、提供信息安全服务的**基础设施**，核心是解决"公钥究竟属于谁"的信任问题。

| 组成部件 | 职责 | 考试要点 |
|---|---|---|
| **CA**（认证中心） | 签发、吊销、管理证书，是信任锚 | 核心权威机构，用自己的私钥签证书 |
| **RA**（注册机构） | 受理申请、核验申请者真实身份 | **只审核不签发**，是 CA 的延伸 |
| 证书库 / 目录服务 | 发布证书与 CRL，供查询（常基于 LDAP） | 证书是公开的，可自由下载 |
| **CRL**（证书吊销列表） | 定期发布的已吊销证书清单 | 有更新延迟 |
| **OCSP**（在线证书状态协议） | 实时查询单张证书状态 | 解决 CRL 延迟问题，但有性能与隐私开销 |
| 密钥管理 / KMC | 密钥生成、存储、备份、恢复、托管 | 国密体系中加密证书密钥由 KMC 托管 |
| 终端实体 | 证书持有者与使用方 | 人、设备、系统、服务 |

### 1.2 X.509 v3 证书主要字段（选择题考点）

版本号、序列号（CA 内唯一）、签名算法标识、**颁发者（Issuer）**、**有效期（NotBefore / NotAfter）**、**主体名（Subject）**、**主体公钥信息**、扩展项（密钥用途 KeyUsage、扩展密钥用途、CRL 分发点、基本约束 CA:TRUE 等）、**CA 对该证书的数字签名**。

> **关键理解**：证书的本质是"**CA 用自己的私钥，对『用户身份 + 用户公钥』这段内容做的数字签名**"。所以验证证书 = 用 CA 的公钥解签名，比对内容是否被篡改。

### 1.3 证书验证四步（案例题常考完整流程）

1. **验证签名**：用颁发者（上级 CA）的公钥解密证书签名，与重新计算的摘要比对；
2. **验证有效期**：当前时间是否落在有效期区间内；
3. **验证吊销状态**：查 CRL 或 OCSP，确认未被吊销；
4. **验证证书链**：逐级向上回溯，直到**自签名的根证书（信任锚）**，根证书必须存在于本地信任库中。

### 1.4 数字签名 + 数字信封（综合题必考组合流程）

**数字签名**（提供完整性 + 认证 + **不可否认**）：

```
发送方：报文 → Hash 摘要 → 用【发送方私钥】加密摘要 = 签名 → 原文 + 签名 一起发送
接收方：原文重算摘要 A；用【发送方公钥】解密签名得摘要 B；A == B 则通过
```

**数字信封**（提供**机密性**，解决非对称加密大数据量效率低的问题）：

```
发送方：随机生成【对称会话密钥 K】→ 用 K 加密报文（快）→ 用【接收方公钥】加密 K（慢但数据量小）→ 密文 + 数字信封 一起发送
接收方：用【接收方私钥】解出 K → 用 K 解密密文
```

**两者组合（既保密又防抵赖）**：

> 标准顺序是"**先签名，后加密**"（Sign-then-Encrypt）。
> 若先加密后签名，签名作用在密文上，接收方无法就明文内容举证，且密文一旦被替换签名也随之失效。**这是经典陷阱选项。**

### 1.5 国密双证书体系（信创场景必写）

国密标准（GM/T 0015、GM/T 0024）采用**双证书**：

| 证书 | 用途 | 密钥对来源 | 特点 |
|---|---|---|---|
| **签名证书** | 身份认证、数字签名 | **用户端自行生成**（如 USBKey 内） | 私钥永不离开介质，**不可托管、不可备份**，保证不可否认性 |
| **加密证书** | 密钥协商、数据加密 | **KMC（密钥管理中心）生成并托管** | 可备份恢复，保证数据可解密、可审计 |

> 案例/论文中写出"**签名密钥对在用户端产生、加密密钥对由 KMC 托管**"，是区分普通考生与专业架构师的标志性细节。

### 1.6 其他信任模型

- **层次（树状）模型**：根 CA → 中间 CA → 终端，主流（如 Web PKI）；
- **网状 / 交叉认证**：多个 CA 互相签名，对等互信；
- **信任网（Web of Trust）**：PGP 使用，用户相互背书，**无中心 CA**；
- **桥 CA**：连接多个独立 PKI 域的中介。

## 二、认证加密（AEAD）与安全协议

### 2.1 加密与认证的三种组合方式（选择题高频排序题）

| 组合方式 | 顺序 | 安全性 | 典型应用 |
|---|---|---|---|
| **Encrypt-then-MAC** | 先加密密文，再对**密文**算 MAC | ✅ **最安全，推荐** | IPsec |
| MAC-then-Encrypt | 先算 MAC，再连同明文与 MAC 一起加密 | ⚠️ 存在 Padding Oracle 等风险 | TLS 1.2 及以前 |
| Encrypt-and-MAC | 对明文分别加密和算 MAC | ⚠️ MAC 泄露明文信息 | SSH |

> 结论：**Encrypt-then-MAC 最优**。因为先验证密文的 MAC 再解密，可避免攻击者利用解密过程的信息泄露（Padding Oracle）做适应性攻击。

### 2.2 AEAD（Authenticated Encryption with Associated Data）

**一次性同时提供 保密性 + 完整性 + 数据源认证**，还提供 **附加认证数据 AAD**（如 IP 头、端口号等需认证但不需加密的字段）。

| 模式 | 构成 | 备注 |
|---|---|---|
| **GCM** | CTR 加密 + GMAC（GHASH）认证 | 主流，可并行，硬件加速好；**IV/nonce 绝不可复用**（复用会导致密钥恢复，灾难性） |
| CCM | CTR 加密 + CBC-MAC 认证 | 需两遍处理，效率略低，用于 802.11i/WPA2 |
| ChaCha20-Poly1305 | 流密码 + Poly1305 | 无硬件加速的移动/低端设备首选，TLS 1.3 标准套件 |
| SM4-GCM / SM4-CCM | 国密分组 + 认证模式 | 信创改造中的对应选型 |

### 2.3 安全协议速查

| 协议 | 层次 | 要点 |
|---|---|---|
| **Kerberos** | 应用层认证 | 基于**对称密钥**与可信第三方 **KDC**（AS + TGS）；票据 TGT；用**时间戳**防重放；默认端口 88；**要求时钟同步**；解决"单点登录 SSO" |
| **TLS/SSL** | 传输层与应用层之间 | 1.2 完整握手 2-RTT，1.3 为 1-RTT（会话恢复 0-RTT）；国密套件遵循 **GM/T 0024 双证书** |
| **IPsec** | 网络层 | **AH**（协议号 51，仅认证与完整性，**不加密**）、**ESP**（协议号 50，加密 + 可选认证）；**SA 安全关联**由 SPI 标识；传输模式 / 隧道模式；IKE 密钥交换（UDP 500 / 4500） |
| **S/MIME** | 应用层（邮件） | 基于 **X.509 证书**体系 |
| **PGP / GPG** | 应用层（邮件） | 基于**信任网**，无中心 CA，密钥环自行背书 |
| **HTTPS** | — | HTTP over TLS，默认 443 |
| **SET** | 电子商务 | 早期信用卡交易协议，双签名 |

## 三、访问控制模型

### 3.1 三大经典模型（必考）

| 模型 | 全称 | 控制依据 | 特点 | 典型场景 |
|---|---|---|---|---|
| **DAC** | 自主访问控制 | 客体的属主自行决定授权（ACL / 能力表） | 灵活、实现简单，**安全性低**，无法抵御木马 | 文件系统（Linux rwx）、数据库 GRANT |
| **MAC** | 强制访问控制 | 系统按**安全标签**（主体安全级 vs 客体安全级）强制判定，用户不能自行更改 | 安全性最高，灵活性差，多用于涉密/军工 | 多级安全系统 SELinux |
| **RBAC** | 基于角色的访问控制 | 用户 → **角色** → 权限（授权给角色而非个人） | 权限变更只需改角色，**管理成本最低**，最符合企业组织形态 | 绝大多数企业信息系统 |

**RBAC 三原则**：**最小权限**、**职责分离（SoD）**、**角色继承**。
RBAC96 家族：**RBAC0**（基础）、**RBAC1**（角色继承）、**RBAC2**（约束：互斥角色、基数约束、先决条件）、**RBAC3**（1+2 合集）。

**ABAC（基于属性的访问控制）**：依据**主体属性、客体属性、环境属性**（如时间、地点、设备）动态决策，策略用 XACML 描述。**粒度最细、最灵活，但策略管理与性能开销大**。演进路径常写作 **DAC → MAC → RBAC → ABAC（零信任架构下的主流选择）**。

### 3.2 四大安全模型（MAC 的理论基础，选择题送分/送命题）

| 模型 | 目标 | 规则 | 记忆 |
|---|---|---|---|
| **BLP**（Bell-LaPadula） | **保密性** | 简单安全特性：**不可上读**（no read up）；*（星）特性：**不可下写**（no write down） | **不上读、不下写** —— 防信息从高密级流向低密级 |
| **Biba** | **完整性** | **不可下读**（no read down）、**不可上写**（no write up） | **不下读、不上写** —— 与 BLP **完全相反**，防低完整性数据污染高完整性 |
| **Clark-Wilson** | **完整性**（商业场景） | **良构事务**（Well-formed Transaction，数据只能经程序改写）、**职责分离**（Separation of Duty）、审计 | 关键词：**受控数据项 CDI、转换过程 TP、审计**；面向"账本、交易"类应用 |
| **Chinese Wall**（中国墙） | **利益冲突** | 主体一旦访问过某利益冲突类的信息，即被禁止访问同类中的其他客体 | 金融、咨询、律所（投行部与研究所之间的信息隔离墙） |

> 记忆对照表（一表定胜负）：

| | 读取方向 | 写入方向 |
|---|---|---|
| **BLP（保密）** | 不上读 ↓只能读同级或更低 | 不下写 ↓只能写同级或更高 |
| **Biba（完整）** | 不下读 ↓只能读同级或更高 | 不上写 ↓只能写同级或更低 |

### 3.3 其他访问控制形态

- **TBAC（基于任务的访问控制）**：权限随**工作流任务**的推进动态授予与收回，适合 OA / 审批流；
- **PBAC / 策略中立访问控制**：以策略为核心统一表达 DAC/MAC/RBAC；
- **零信任（Zero Trust）**："**永不信任，始终验证**"，默认内网也不受信，基于**持续认证 + 动态授权 + 微隔离**，是 ABAC 的工程落地范式（NIST SP 800-207）。

## 四、等保 2.0 与商用密码应用安全性评估（密评）

### 4.1 等保 2.0（网络安全等级保护）

| 维度 | 内容 |
|---|---|
| 核心标准 | **GB/T 22239-2019**《网络安全等级保护基本要求》；GB/T 22240-2020《定级指南》；GB/T 28448-2019《测评要求》 |
| 保护对象 | 由"信息系统"扩展为"**网络**"，覆盖**云（云计算）、移（移动互联）、物（物联网）、工（工业控制系统）、大（大数据）**五类扩展要求 |
| 防护框架 | "**一个中心、三重防护**"：安全管理中心 + 安全**计算环境**、安全**区域边界**、安全**通信网络** |
| 安全等级 | 第一级（自主保护）～ 第五级（专控保护），常见为**二级、三级** |
| 定级流程 | 确定定级对象 → 初步确定等级 → **专家评审** → 主管部门审核 → **公安机关备案** |
| 测评周期 | 三级及以上**每年至少一次**；二级原则上**每两年一次**（部分行业/地区要求每年） |
| 测评结论 | 优 / 良 / 中 / 差 |

### 4.2 密评（商用密码应用安全性评估）

| 维度 | 内容 |
|---|---|
| 法律依据 | **《密码法》第二十七条**（2020-01-01 施行）、《商用密码管理条例》（2023 修订） |
| 核心标准 | **GB/T 39786-2021**《信息系统密码应用基本要求》 |
| 适用范围 | **关键信息基础设施**必须开展；等保三级及以上系统通常同步开展 |
| 技术四层面 | **物理和环境、网络和通信、设备和计算、应用和数据** |
| 管理四层面 | **管理制度、人员管理、建设运行、应急处置** |
| 评估要求 | 投入运行前须评估；通过后方可运行；**运行后每年至少评估一次** |
| 结论 | 符合 / **基本符合**（得分达阈值且**无高风险项**）/ 不符合 |

### 4.3 等保 vs 密评：一句话区分（案例题高频辨析）

| 对比项 | 等保 2.0 | 密评 |
|---|---|---|
| 关注点 | 系统**整体安全**：技术 + 管理 + 物理 + 人员 | **密码应用是否合规、正确、有效** |
| 主管部门 | 公安（网安） | 密码管理部门 |
| 核心问题 | "系统防护到不到位？" | "密码用得对不对、算法合规不合规？" |
| 关系 | 等保是**全面体检** | 密评是**专项检查**，二者**互为补充、不能互相替代** |

> **典型失分点**：把"用了国密算法"等同于"通过密评"。密评还要求**密码产品具备《商用密码产品认证证书》**、密钥全生命周期管理合规、密码服务由合规密码机提供等。

### 4.4 相关法律法规时间轴

| 法律法规 | 施行时间 |
|---|---|
| 《网络安全法》 | 2017-06-01 |
| 《密码法》 | 2020-01-01 |

## 五、考法拆解与得分逻辑

### 5.1 综合知识（选择题）

**考法 1｜证书流程判断**
"关于数字证书的说法，正确的是"：常设陷阱——证书可被**任何人**用 CA 公钥验证（证书本身不需要保密）；RA **不签发**证书；**根 CA 证书是自签名的**；吊销状态需查 CRL/OCSP 而非仅在本地校验。

**考法 2｜签名与信封顺序**
"先加密后签名"是**错误**的，正确是"**先签名后加密**"。

**考法 3｜访问控制模型配对**
题干给场景选模型：
- "某政府机密文件系统按密级管控，用户不能自行授权他人访问" → **MAC**；
- "某公司将员工权限按岗位分配，员工调动只需调整岗位" → **RBAC**；
- "某系统根据访问时间、终端类型、用户部门动态决定是否放行" → **ABAC**；
- "防止内部人员同时担任会计与出纳" → RBAC 的**职责分离（SoD）**；
- "证券公司防止投行部与研究部串通" → **Chinese Wall**。

**考法 4｜BLP / Biba 规则**
直接给出"某主体安全级为秘密，能否读取机密级文件" → BLP 下**不能**（不可上读）；能否写入公开级文件 → BLP 下**不能**（不可下写）。

**考法 5｜协议归属**
AH 不加密、ESP 加密；Kerberos 用对称密钥 + 时间戳；PGP 用信任网、S/MIME 用 X.509；IKE 负责密钥交换。

### 5.2 案例分析（主观题）

**模板（严格遵守，否则失分）**：

> ① **引用题干事实**："题干中系统是 X 级等保系统 / 涉及跨部门数据交换 / 存在内部人员越权风险……"
> ② **对应方法/原则**：点明所选控制措施与标准依据（如"依据 GB/T 39786 技术四层面"）；
> ③ **提出可执行动作**：措施 + 责任主体 + 落地机制（制度、流程、工具）。

**场景 A：等保/密评合规整改类**

答题要点按四层面展开：**身份鉴别、访问控制、数据完整性、数据机密性、不可否认性、审计与日志**，再补管理机制（密码管理制度、人员培训、应急预案与演练、密钥全生命周期管理）。

**场景 B：越权与内部威胁类**

答题链条：**权限模型选型（RBAC + SoD）→ 最小权限原则 → 账号生命周期管理（入职/调岗/离职） → 敏感操作双人复核 → 统一审计日志（防篡改、留存 ≥6 个月）→ 定期权限复核**。

**场景 C：数据传输与认证类**

答题链条：**HTTPS/国密 TLS 保障传输机密性 → 双证书实现双向身份鉴别 → SM2 签名实现抗抵赖 → SM3/HMAC-SM3 保障完整性 → SM4-GCM 实现认证加密 → 时间戳 + nonce 防重放**。

**加分术语**：一个中心三重防护、纵深防御、最小权限、职责分离、双因子认证、密钥全生命周期管理、国密双证书、GM/T 0024、商用密码产品认证证书。

### 5.3 论文素材

- **难点段**：系统涉及多角色跨部门协作，存在越权访问与操作抵赖风险，且需满足等保三级与密评要求；
- **方案段**：构建"**身份鉴别—访问控制—传输安全—审计追溯**"四层安全防护体系。采用 **RBAC + ABAC 混合模型**（角色授予基础权限，属性策略做动态约束，敏感岗位实施职责分离）；基于 **PKI/CA 双证书**实现强身份鉴别与操作抗抵赖；传输采用**国密 TLS（GM/T 0024）**，数据加密使用 **SM4-GCM**，完整性使用 **SM3**；建设统一审计中心，日志集中留存且防篡改；
- **结果段**：通过等保三级测评与密评，实现权限最小化与操作可追溯，未发生越权与数据泄露事件，权限复核从人工周级缩短为自动日级。

## 六、五分钟自测

1. RA 的核心职责是什么？（答案：审核申请者身份，**不签发证书**）
2. 数字签名与数字信封组合时，正确顺序是什么？（答案：先签名，后加密）
3. 国密双证书中，哪一类的密钥对必须在用户端生成、不可托管？（答案：签名证书密钥对）
4. 三种加密/认证组合中最安全的是哪种？（答案：Encrypt-then-MAC）
5. BLP 模型的两条规则是什么？（答案：不可上读、不可下写）
6. 保障数据完整性（防低质量数据污染高质量数据）应选 BLP 还是 Biba？（答案：Biba）
7. 等保 2.0 的防护框架是什么？（答案：一个中心、三重防护）
8. 密评的四个技术层面是什么？（答案：物理和环境、网络和通信、设备和计算、应用和数据）
9. 等保与密评能否互相替代？（答案：**不能**，全面体检 vs 专项检查）
10. Kerberos 用什么机制防重放？（答案：时间戳，因此要求时钟同步）

## 七、速记口诀

- **RA 审核、CA 签发、CRL 查吊销、根证书自签名**；
- **先签名，后加密；对称加密快，非对称送钥匙**；
- **签名密钥端内生、加密密钥 KMC 托管**；
- **BLP 保密不上读不下写；Biba 完整反过来**；
- **DAC 自主、MAC 强制、RBAC 按岗、ABAC 看属性、零信任永不信**；
- **云移物工大，一个中心三重防护**；
- **等保查全身，密评查密码，两本账不能混**。
