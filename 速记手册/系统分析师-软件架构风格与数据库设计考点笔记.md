## 一、软件架构风格

### 1.1 经典五大类（Garlan & Shaw 分类，必背）

| 大类 | 具体风格 | 核心机制 | 典型优点 | 典型缺点 |
|---|---|---|---|---|
| **数据流风格** | **批处理序列** | 每一步必须完全结束后，下一步才开始，数据以整体为单位传递 | 简单、易于验证 | 无交互、高延迟 |
| | **管道-过滤器** | 每个过滤器独立处理数据流并通过管道传递 | 构件复用性强、可并发、易维护 | 不适合交互；**需统一数据格式**，转换开销大 |
| **调用/返回风格** | **主程序-子程序** | 单线程控制，显式调用 | 结构简单 | 规模受限 |
| | **面向对象（ADT）** | 对象封装数据与方法，通过方法调用交互 | 高内聚低耦合、易维护复用 | 对象标识变化影响调用方 |
| | **分层（层次结构）** | 层间单向依赖，每层为上层提供服务 | 易维护、易扩展、支持复用与标准化 | **性能损耗（多层转发）**；难以界定层边界 |
| **独立构件风格** | **进程通信** | 独立进程通过消息传递（远程调用、同步/异步）协作 | 支持分布式、可容错 | 通信复杂度高 |
| | **事件驱动（隐式调用）** | 构件**注册事件**，事件触发时**由系统隐式调用**相应过程，调用方不直接指定被调用者 | **强松耦合、易扩展新构件** | **放弃了对执行顺序和计算结果的控制**；难调试与验证 |
| **虚拟机风格** | **解释器** | 解析并执行自定义伪代码（引擎 + 存储区） | 灵活、可移植 | **执行效率低** |
| | **基于规则的系统** | 规则库 + 工作内存 + 推理引擎（专家系统） | 擅长复杂推理 | 规则膨胀难维护 |
| **仓库风格** | **数据库系统 / 以数据为中心** | 中央数据结构 + 若干独立处理构件共享数据 | 数据集中、易集成 | 数据结构变更影响面大 |
| | **黑板系统** | 知识源独立求解，通过**共享黑板**协作，由中央控制调度 | 适合**无确定求解策略**的复杂问题（语音识别、信号处理） | 难建模、效率低、控制复杂 |
| | 超文本系统 | 网状链接组织信息 | 非线性浏览 | — |

### 1.2 工程化架构风格（案例与论文主战场）

| 风格 | 核心要点 | 优势 | 代价与适用边界 |
|---|---|---|---|
| **C/S 两层** | 客户端承担业务逻辑，服务端是数据库 | 交互性强 | 客户端臃肿、升级维护困难、安全性较低 |
| **C/S 三层（表现/业务/数据）** | 中间层封装业务逻辑 | 易维护、易扩展、安全性好 | 复杂度上升 |
| **B/S** | 浏览器为统一客户端 | **零安装、易升级、跨平台** | 交互与离线能力受限；**瘦客户端对网络依赖强** |
| **MVC / MVP / MVVM** | 分离模型、视图、控制器 | 职责分离、可测试 | MVC 中 View 与 Model 仍有耦合；MVVM 用数据绑定解决 |
| **SOA** | 服务 + **ESB 企业服务总线**，服务注册与编排 | 遗留系统集成、异构互通 | **ESB 易成性能瓶颈与单点**；治理复杂 |
| **微服务** | 服务按业务边界拆分，**独立部署、独立数据库、去中心化治理**，轻量通信（REST/gRPC） | 独立演进、弹性伸缩、技术异构 | **分布式复杂度高**：网络延迟、分布式事务、数据一致性、运维与监控成本剧增 |
| **事件驱动架构 EDA** | 事件生产者—通道—消费者，消息队列/事件总线解耦 | **极致松耦合、高吞吐、易扩展** | 最终一致性；事件顺序与幂等需额外设计 |
| **CQRS** | **命令与查询职责分离**，读写模型各自优化 | 读写分别优化、高性能查询 | 读模型**最终一致**；复杂度高 |
| **事件溯源 Event Sourcing** | 不存当前状态，**存不可变事件序列**，状态由事件重放得出 | 完整审计追溯、可回溯任意时点 | 查询需投影；事件结构演进困难 |
| **六边形（端口-适配器）** | 领域在中心，外围通过端口与适配器接入 | 业务逻辑与技术设施彻底解耦、易测试 | 抽象层次多，学习成本 |
| **微内核（插件式）** | 核心引擎 + 可插拔插件 | 易扩展（如 Eclipse、IDE） | 内核设计难度大 |
| **Serverless / FaaS** | 按调用计费，免运维 | 极速弹性、成本按需 | 冷启动、状态管理受限、供应商锁定 |
| **Service Mesh** | 服务治理能力下沉到**边车（Sidecar）代理** | 业务代码零侵入 | 增加网络跳数与运维复杂度 |
| **P2P** | 节点对等，无中心 | 高容错、可扩展 | 管理困难、安全性差 |

### 1.3 选型决策（案例题论证骨架）

```
业务约束 → 质量属性优先级 → 架构风格
├─ 高吞吐、批处理、无交互   → 管道-过滤器 / 批处理序列
├─ 求解策略不确定（AI 推理） → 黑板系统
├─ 需要频繁扩展新处理逻辑   → 事件驱动（隐式调用）/ 微内核
├─ 企业遗留系统集成、异构   → SOA + ESB
├─ 高并发、快速迭代、团队自治 → 微服务
├─ 交易量小、追求快速交付   → 单体分层（不要为微服务而微服务）
└─ 读写压力极端不均衡       → CQRS + 读写分离
```

> **论证要点**：案例题问"选哪种架构"，**必须写出所放弃的东西**（如"微服务带来分布式事务与运维复杂度，本系统规模小、团队不足，故采用分层单体架构"）——**只说优点不说代价，是拿不到高分的**。

## 二、质量属性与架构评估（ATAM）

### 2.1 质量属性场景的六要素（必背）

| 要素 | 含义 |
|---|---|
| **刺激源** | 产生刺激的实体（人、系统、外部事件） |
| **刺激** | 到达系统时需要考虑的条件（事件、请求） |
| **环境** | 刺激发生时的系统状态（正常、过载、降级） |
| **制品** | 被刺激的对象（系统、构件、服务） |
| **响应** | 刺激到达后系统采取的行动 |
| **响应度量** | 对响应的**可量化**度量（如"2 秒内完成""99.99% 可用"） |

> **关键**：场景必须**可度量**。写"系统响应要快"不合格，写"在 1000 并发下，95% 请求响应时间 ≤ 2 秒"才合格。

### 2.2 ATAM 四个核心概念（易混，必考）

| 概念 | 定义 | 举例 |
|---|---|---|
| **敏感点 Sensitivity Point** | 构件特性，**对某个质量属性的达成至关重要** | 数据复制份数 → 影响可用性 |
| **权衡点 Tradeoff Point** | 同时影响**多个**质量属性的特性 | **加密级别**：提高安全性却降低性能 |
| **风险 Risk** | 潜在的、有问题的架构决策 | 依赖单一消息中间件，存在单点故障风险 |
| **非风险 Non-risk** | 经分析认为安全、良好的决策 | — |

> 速记：**权衡点 = 多个质量属性的敏感点**（一个点同时"牵动"两边）。

### 2.3 ATAM 评估过程（九步 / 四阶段）

**阶段一 呈现**：① 介绍 ATAM → ② 介绍业务动机 → ③ 介绍架构
**阶段二 调查与分析**：④ 识别架构方法与风格 → ⑤ 生成**质量属性效用树** → ⑥ 分析架构方法（对高优先级场景）
**阶段三 测试**：⑦ 全体干系人**头脑风暴**并对场景分级（投票：重要度 × 难度） → ⑧ 再次分析架构方法
**阶段四 报告**：⑨ 呈现结果（效用树、场景、风险与非风险、敏感点与权衡点）

**效用树结构**：**效用（Utility）** → 质量属性（性能/安全性/可用性/可修改性…） → 属性细分 → **具体场景（刺激 + 响应度量）**，并标注 **(重要度, 实现难度)**，形如 (H, H)。

其他评估方法：**SAAM**（最早、面向可修改性，用场景评估）、**CBAM**（在 ATAM 基础上加入**成本-收益**经济建模）。

### 2.4 质量属性战术（选择题与论文的高分素材）

| 质量属性 | 战术分类 | 典型措施 |
|---|---|---|
| **可用性** | 错误检测 | **心跳 / 命令-响应 / 异常检测** |
| | 错误恢复 | **主动冗余（热备）、被动冗余（冷备）、备件、检查点/回滚、状态再同步、表决** |
| | 错误预防 | 进程监视器、事务、从服务中移除、重启 |
| **性能** | 资源需求 | 减少处理的数据量、降低计算频率、限制队列长度 |
| | 资源管理 | **引入并发、增加可用资源、维持多副本** |
| | 资源仲裁 | 调度策略：FIFO、固定优先级、动态优先级、静态调度 |
| **安全性** | 抵抗攻击 | 身份认证、授权、加密、完整性校验、**限制暴露点、限制访问** |
| | 检测攻击 | **入侵检测系统 IDS** |
| | 从攻击恢复 | 状态恢复、识别攻击者 |
| **可修改性** | 局部化变更 | 维持语义一致性、预期期望的变更、**泛化模块**、限制可能的选择 |
| | 防止连锁反应 | **信息隐藏、维持现有接口、限制通信路径、使用仲裁者（中介）** |
| | 推迟绑定时间 | **配置文件、运行时注册、多态、组件更换**、遵守已定义协议 |
| **可测试性** | — | 记录/回放、接口与实现分离、提供专用测试接口 |
| **易用性** | — | 分离用户界面、支持撤销/取消、维护用户模型 |

## 三、数据库设计：E-R 模型与关系模式转换

### 3.1 三级模式与两级映像（选择题必考）

| 模式 | 别名 | 说明 |
|---|---|---|
| **外模式** | 子模式 / 用户模式 | 用户能看到和使用的局部数据，对应**视图**，可有多个 |
| **模式** | 逻辑模式 / 概念模式 | 全体数据的整体逻辑结构（基本表），**只有一个** |
| **内模式** | 存储模式 / 物理模式 | 数据在存储介质上的物理结构与存取方法，**只有一个** |

**两级映像与两种独立性（必考对应关系）**：

- **外模式 / 模式 映像** → 数据的**逻辑独立性**（模式变了，改映像即可，应用程序不必改）；
- **模式 / 内模式 映像** → 数据的**物理独立性**（存储结构变了，模式不变，应用更不受影响）。

### 3.2 E-R 模型元素

- **实体**（矩形）：客观存在并可相互区别的事物（可以是人、物、事件）；
- **属性**（椭圆）：**简单/复合**、**单值/多值**、**存储/派生**属性；
- **码**：能唯一标识实体的属性集；
- **弱实体**（双线矩形）：不能独立存在，依赖强实体（如"订单项"依赖"订单"）；
- **联系**（菱形）：**1:1**、**1:N**、**M:N**；联系的**基数约束**（min, max）；
- **泛化/特化（ISA）**：三角形 + 连线，子类继承父类属性。

### 3.3 E-R 转关系模式的规则（案例题必考，逐条背）

| 转换对象 | 规则 |
|---|---|
| **实体** | 一个实体 → 一个关系模式；属性 → 列；实体码 → 主键 |
| **1:1 联系** | 两种做法：① 独立成关系模式，主键取**任一端**的码；② **合并到任一端**实体模式，加入另一端的码作为外键（更常用） |
| **1:N 联系** | 两种做法：① 独立成关系模式，主键取 **N 端**的码；② **合并到 N 端**实体模式，加入 **1 端**的码作为外键（更常用，如"部门-员工"把部门号写进员工表） |
| **M:N 联系** | **必须独立成关系模式**，主键 = **两端实体码的组合**（复合主键），两端码各自为外键（如"学生-课程"联系转为"选课"表） |
| **多元（三元及以上）联系** | 独立成关系模式，主键 = **各参与实体码的组合** |
| **弱实体** | 独立成关系模式，主键 = **强实体的码 + 弱实体的部分码** |
| **多值属性** | 独立成关系模式，与实体码组成主键 |
| **泛化/特化** | 父类建表 + 子类建表（主键同父类码）；或只建子类表（父类属性冗余进各子表）；或单表 + 类型判别列 |

### 3.4 数据库设计六步骤

**需求分析**（数据流图 + 数据字典）→ **概念结构设计**（**E-R 图**，与具体 DBMS 无关）→ **逻辑结构设计**（E-R 转关系模式 + **规范化**优化）→ **物理设计**（存储结构、索引、分区、存取路径）→ **数据库实施**（建库、装载、试运行）→ **运行维护**（备份恢复、性能调优、重组织与重构造）。

## 四、关系规范化（范式）

### 4.1 范式层级与判定（必考）

| 范式 | 条件 | 消除的问题 |
|---|---|---|
| **1NF** | 每个分量都是**不可再分**的原子值，无重复组 | 消除重复组（如"电话1、电话2"列） |
| **2NF** | 在 1NF 上，**每个非主属性完全函数依赖于候选码** | 消除非主属性对码的**部分函数依赖**（典型：联合主键中主属性单列就能决定某个非主属性） |
| **3NF** | 在 2NF 上，**非主属性不传递依赖于码** | 消除**传递函数依赖**（如 学号→系号，系号→系主任，则系主任传递依赖学号） |
| **BCNF** | 在 3NF 上，**每一个决定因素都包含码** | 消除**主属性**对码的部分/传递依赖（3NF 未处理的"主属性间依赖"问题） |
| **4NF** | 消除非平凡的**多值依赖** | 一个表中存在多个独立的一对多关系（如 课程-教师-教材） |
| **5NF** | 消除**连接依赖** | 分解后能无损连接还原 |

**判定口诀**（由低到高）：**1NF 原子 → 2NF 无部分依赖 → 3NF 无传递依赖 → BCNF 决定因素必含码 → 4NF 无多值依赖**。

### 4.2 相关概念

- **函数依赖**：X → Y（X 值确定则 Y 值确定）；
- **完全函数依赖** vs **部分函数依赖**（依赖 X 的真子集即可）；
- **传递函数依赖**：X→Y，Y→Z，且 Y 不→X，则 X→Z 为传递依赖；
- **候选码**：能唯一决定全部属性且无冗余的**最小**属性集；**主属性** = 包含在任一候选码中的属性；
- **无损连接分解**：分解后通过自然连接能还原原关系（不丢信息）；
- **保持函数依赖**：分解后原有的函数依赖仍能在各子模式上被保持。

> **考试标准**：关系模式分解至少要达到 **3NF**，且应尽可能做到**无损连接 + 保持函数依赖**。

### 4.3 反规范化（案例题常考"为什么反而要加冗余"）

| 手段 | 说明 |
|---|---|
| 增加冗余列 | 把常用关联字段直接冗余进主表，减少 JOIN |
| 增加派生列 | 直接存计算结果（如订单金额合计），免去实时聚合 |
| 重新组表 | 将频繁一起查询的两个表合并 |
| **水平分割** | 按行拆分（按时间、按地区、按租户） |
| **垂直分割** | 按列拆分（热列与冷列分开，大字段单独存放） |

**权衡**：**以空间换时间、以冗余换性能**。代价是数据冗余、更新异常、需额外保证一致性（触发器/应用层/异步补偿）。

## 五、事务与并发控制

### 5.1 事务 ACID

**原子性 A**（全做或全不做）、**一致性 C**（从一个一致状态到另一个一致状态）、**隔离性 I**（并发事务互不干扰）、**持久性 D**（提交后永久生效）。

### 5.2 并发引发的三/四类问题

| 问题 | 现象 |
|---|---|
| **丢失修改** | 两个事务同时改同一数据，后提交覆盖先提交，先前的修改丢失 |
| **不可重复读** | 同一事务内两次读同一数据，结果不同（因另一事务**修改并提交**） |
| **读"脏"数据** | 读到了另一事务**未提交**的中间结果，而该事务随后回滚 |
| 幻读 | 同一事务两次按条件查询，第二次多出/少了符合该条件的行（因另一事务**插入/删除**） |

### 5.3 封锁机制与三级封锁协议

**锁类型**：**排他锁 X**（写锁，加 X 后其他事务既不能读也不能写）、**共享锁 S**（读锁，加 S 后其他事务可读不可写）。

**三级封锁协议（必背对应表）**：

| 协议 | 规则 | 解决 |
|---|---|---|
| **一级** | 修改数据前加 X 锁，**直到事务结束**才释放 | 丢失修改 |
| **二级** | 一级 + 读数据前加 S 锁，**读完即可释放** | 丢失修改 + 读"脏"数据 |
| **三级** | 一级 + 读数据前加 S 锁，**直到事务结束**才释放 | 丢失修改 + 读脏 + **不可重复读** |

### 5.4 两段锁协议与死锁

- **两段锁协议 2PL**：事务分为**加锁阶段**与**解锁阶段**，解锁后不得再加锁。遵守 2PL 是**并发调度可串行化的充分条件**（非必要）；
- **死锁**：两个及以上事务互相等待对方持有的锁。处理三类：**预防**（一次封锁法、顺序封锁法）、**检测**（超时法、**等待图法**）、**解除**（撤销代价最小的事务）；
- **活锁**（饥饿）：某事务长期得不到锁，用**先来先服务**策略解决。

### 5.5 隔离级别（由低到高）

| 级别 | 可避免 | 性能 |
|---|---|---|
| 读未提交 Read Uncommitted | — | 最高 |
| 读已提交 Read Committed | 读脏 | 较高（Oracle / SQL Server 默认） |
| 可重复读 Repeatable Read | 读脏、不可重复读 | 中（**MySQL InnoDB 默认**） |
| 可串行化 Serializable | 全部（含幻读） | 最低 |

### 5.6 备份与故障恢复

| 备份类型 | 说明 |
|---|---|
| **完全备份** | 备份全部数据，恢复最快，占用空间最大 |
| **增量备份** | 只备份上次备份以来变化的部分，空间省，恢复需回溯全链 |
| **差异备份** | 备份上次完全备份以来的变化，恢复只需"完全 + 最近一次差异" |

**故障类型**：事务内部故障（**UNDO 回滚**）、系统故障（**UNDO + REDO**）、介质故障（**重装副本 + 重做已提交事务**）、病毒与人为破坏。
**检查点（Checkpoint）**：缩短故障恢复时间，只需处理检查点之后的事务。

## 六、物理设计、优化与新技术速查

### 6.1 索引与优化

- **B+ 树索引**：关系库主流，适合范围查询与排序；**哈希索引**适合等值查询，不支持范围；**位图索引**适合低基数列（性别）；**全文索引**用于文本检索；
- **索引双面性**：**加快查询，减慢增删改**，且占用存储；
- **建索引建议**：主键、外键、高频查询条件列、连接列、排序列；**不宜**建在低选择性列、频繁更新的列、很少被查询的列；
- **SQL 优化要点**：避免 `SELECT *`；**避免在索引列上使用函数或表达式**（会导致索引失效）；避免 `LIKE '%xxx'` 前置通配符（索引失效）；`OR` 改写为 `UNION`；大表驱动小表时用 `EXISTS` 替代 `IN`；避免隐式类型转换；
- **架构层优化**：读写分离、分库分表（水平/垂直）、缓存（Redis）、连接池、异步化、热点数据打散。

### 6.2 分布式与 CAP / BASE

| 理论 | 内容 |
|---|---|
| **CAP** | **一致性 C、可用性 A、分区容错性 P** 三者不可兼得；网络分区（P）在分布式下必然存在，故实际是在 **C 与 A 之间权衡**（CP 或 AP） |
| **BASE** | **基本可用**（Basically Available）、**软状态**（Soft state）、**最终一致性**（Eventually consistent）——对 CAP 中 AP 的工程化延伸 |
| 一致性方案 | 强一致（2PC/XA、Raft/Paxos）、最终一致（本地消息表、事务消息、TCC、Saga 补偿、最大努力通知） |

### 6.3 NoSQL 四类与数据仓库

| 类型 | 代表 | 适用场景 |
|---|---|---|
| **键值** | Redis | 缓存、会话、排行榜、分布式锁 |
| **文档** | MongoDB | 半结构化、Schema 多变的业务数据 |
| **列族** | HBase、Cassandra | 海量写入、宽表、时序 |
| **图** | Neo4j | 关系深度遍历（社交、风控、知识图谱） |

**OLTP vs OLAP**：

| OLTP（联机事务处理） | OLAP（联机分析处理） |
|---|---|
| 面向业务操作，高并发短事务 | 面向分析决策，复杂聚合查询 |
| 数据实时、当前、细节 | 数据历史、集成、汇总 |
| 规范化设计（3NF） | **反规范化设计（星型/雪花模型）** |
| 关注吞吐与响应时间 | 关注查询灵活性与扫描效率 |

**数据仓库建模**：**事实表**（度量值 + 外键）+ **维度表**（描述性属性）；**星型模型**（维度表直接连事实表，非规范化，查询快）；**雪花模型**（维度表再规范化，省空间、JOIN 多）；**ETL**（抽取 Extract、转换 Transform、加载 Load）；数据集市、数据湖、湖仓一体。

## 七、考法拆解与得分逻辑

### 7.1 综合知识（选择题）

**考法 1｜架构风格归类**
题干给"编译器" → **管道-过滤器**（词法/语法/语义/代码生成逐级处理）；给"专家系统/规则引擎" → **基于规则的系统**；给"JVM/脚本引擎" → **解释器**；给"语音识别、信号处理、无确定求解策略" → **黑板系统**；给"事件触发、隐式调用、松耦合" → **事件驱动**。

**考法 2｜风格特性辨析**
分层风格的缺点 = **性能损耗 + 层边界难界定**；事件驱动/隐式调用的缺点 = **丧失对执行顺序和结果的控制**；解释器的缺点 = **执行效率低**；管道-过滤器的缺点 = **需统一数据格式、不适合交互式**。

**考法 3｜ATAM 四概念**
"某参数改变同时提升安全性但降低性能" → **权衡点**；"某参数对可用性影响巨大" → **敏感点**。

**考法 4｜三级模式两级映像**
**外模式/模式 → 逻辑独立性；模式/内模式 → 物理独立性**（考场上最容易记反，务必对照记忆）。

**考法 5｜范式判定**
给出关系模式与函数依赖集，判断属于第几范式、找出违反之处、给出分解方案。

**考法 6｜封锁协议**
"读数据前加共享锁，直到事务结束才释放" → **三级封锁协议**，解决不可重复读。

**考法 7｜E-R 转换**
M:N 联系**必须**独立成表、主键为两端码组合；1:N 联系通常把 1 端码作为外键并入 N 端。

### 7.2 案例分析（主观题）

**题型 A：架构选型论证（大题）**

> ① **引用题干事实**："题干系统日订单峰值 X 万，涉及 A、B、C 三类用户，团队规模 Y 人，要求 7×24 可用且需对接遗留系统 Z……"
> ② **对应方法/原则**：点明质量属性优先级（如"可用性 > 性能 > 可修改性"）与所依据的架构风格/战术；
> ③ **可执行动作**：给出分层/服务划分、关键构件、技术选型，并**明确写出被牺牲的方面与补偿措施**。

**必写内容清单**：
- 架构风格名称 + **为什么选它**（业务约束驱动）；
- 质量属性与战术的对应（如"为达成 99.99% 可用性，采用**主动冗余 + 心跳检测 + 故障自动切换**"）；
- **明确给出权衡点**（如"引入缓存提升性能，代价是数据一致性降级为最终一致，通过失效通知 + 过期时间 + 重试补偿解决"）；
- 风险与非风险（如"依赖单一 MQ 存在单点风险，采用集群 + 镜像队列缓解"）。

**题型 B：E-R 补图与关系模式转换**

- 补全**实体、联系、基数**（尤其注意题干中的"每个/至多/至少一个"）；
- 按 3.3 规则逐条转换，注意 **M:N 必须独立建表**、**1:N 外键落在 N 端**；
- 指出主键（PK）与外键（FK）。

**题型 C：范式问题诊断与改进**

- 找出**部分依赖 / 传递依赖**，指出会造成**数据冗余、插入异常、删除异常、更新异常**；
- 给出分解方案，说明分解后达到 3NF 且**无损连接、保持函数依赖**；
- 若题干提到"查询性能不足"，需顺势讨论**反规范化**及其一致性维护手段。

**主要失分点**：
- 只堆砌风格名称，不结合题干业务约束；
- 只写架构优点、不写代价与补偿（**这是论证书写能力的核心判据**）；
- 范式题只给结论不给依据（必须写出**函数依赖表达式**作为证据）；
- E-R 转换漏掉 M:N 联系表。

### 7.3 论文素材（架构设计方向，最稳妥选题）

- **背景段**：某 XX 系统，业务量、用户量、既有系统痛点（单体臃肿/耦合严重/扩展困难/响应慢/可用性不足）；
- **难点段**：**多质量属性相互制约**（既要高性能又要强一致、既要快速迭代又要稳定可靠）、遗留系统集成、团队能力与工期限制；
- **方案段**（推荐结构）：
  1. **架构风格选型与论证**：分层 + 微服务/事件驱动，说明选型依据与**被放弃的方案及理由**；
  2. **质量属性落地**：性能（多级缓存、读写分离、异步化、分库分表）、可用性（集群、主备切换、熔断限流降级、超时重试）、安全性（认证授权、加密、审计）、可修改性（领域分层、接口抽象、配置化）；
  3. **关键架构决策与权衡**：如**强一致 vs 最终一致**（核心交易用 TCC/本地消息表保证，非核心用最终一致 + 补偿）、**CQRS 读写分离**；
  4. **数据设计**：E-R 建模 → 关系模式 → 规范化到 3NF → 针对热点做反规范化与索引优化；
  5. **治理与演进**：CI/CD、配置中心、服务治理、全链路监控、灰度发布；
- **结果段**：给出量化指标（响应时间下降 X%、可用性从 X 提升到 99.99%、发布周期从周级缩短到日级、故障恢复时间从小时级降到分钟级）。

> **高分提示**：论文中**必须出现权衡讨论**。只写"我用了微服务，效果很好"的论文属于中等偏下；写出"考虑到团队规模与分布式复杂度，核心链路先不拆分，采用模块化单体 + 清晰上下文边界，待团队与治理能力成熟后再演进为微服务"的论文，才有高级分析师的判断力。

## 八、五分钟自测

1. 编译器的词法/语法/语义分析属于哪种架构风格？（答案：**管道-过滤器**）
2. 隐式调用风格最主要的缺点是什么？（答案：**失去对执行顺序和计算结果的控制**）
3. 同时影响多个质量属性的架构特性叫什么？（答案：**权衡点**）
4. 保证"逻辑独立性"的是哪一级映像？（答案：**外模式/模式映像**）
5. E-R 中 M:N 联系转换为关系模式时如何处理？（答案：**必须独立建表，主键为两端码组合**）
6. 3NF 消除了什么依赖？（答案：**非主属性对码的传递函数依赖**）
7. 三级封锁协议能解决哪三类问题？（答案：**丢失修改、读脏数据、不可重复读**）
8. 两段锁协议保证什么？（答案：**并发调度可串行化**，是充分非必要条件）
9. MySQL InnoDB 默认隔离级别是什么？（答案：**可重复读 Repeatable Read**）
10. CAP 中，分布式系统实际是在哪两者间权衡？（答案：**C 一致性与 A 可用性**，P 必须保证）
11. 反规范化的本质权衡是什么？（答案：**以空间换时间、以冗余换性能**）
12. 星型模型与雪花模型的区别？（答案：星型维度表**非规范化**、查询快；雪花维度表**规范化**、省空间但 JOIN 多）

## 九、速记口诀

- **编译管道、专家规则、语音黑板、脚本解释器**；
- **隐式调用松耦合，代价是丢控制权**；
- **外模/模式管逻辑，模式/内模管物理**；
- **敏感点影响一个，权衡点牵动两边**；
- **1NF 原子、2NF 无部分、3NF 无传递、BCNF 决定因素必含码**；
- **一级防丢失、二级防脏读、三级防不可重复读**；
- **M:N 必建表、1:N 外键落 N 端**；
- **规范化消冗余，反规范化换性能**；
- **分区必然在，C 与 A 二选一；BASE 求最终一致**；
- **写架构必写代价，写论文必写权衡**。
