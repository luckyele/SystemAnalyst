# 系统分析师｜需求工程与 UML 建模考点笔记

> 适用科目：综合知识（选择题）+ **案例分析（主观题，必考）** + 论文（高频方向）
> 命题定位：**UML 是案例分析雷打不动的必考题**，形式稳定为"补充图中缺失元素 / 指出并改正错误 / 解释关系语义"；需求工程则常以"需求问题诊断 + 变更控制流程"形式出案例大题，同时是论文最稳妥的选题方向之一。

---

## 一、需求工程

### 1.1 需求的层次（选择题常考归类）

| 层次 | 定义 | 来源 | 说明 |
|---|---|---|---|
| **业务需求** | 组织为什么要做这个系统（目标、愿景） | 投资人、高层管理者 | 写在项目章程/愿景文档中 |
| **用户需求** | 用户要求系统完成什么任务 | 最终用户 | 用**用例模型**描述 |
| **系统需求** | 系统必须提供的功能与约束的总和 | 分析人员 | = 功能需求 + 非功能需求 + 设计约束 |

**系统需求的三种成分**：

- **功能需求**：系统"做什么"（如"支持订单批量导入"）；
- **非功能需求**：系统"做得怎么样"——性能、安全性、可靠性、可用性、可维护性、可扩展性、易用性、可移植性；
- **设计约束**：限定解决方案空间的限制（必须用国产数据库、必须遵守某行业标准、必须支持信创 CPU）。

> 陷阱：题干说"系统响应时间不超过 3 秒"——这是**非功能需求**（性能需求），不是功能需求。

### 1.2 需求获取方法（选择题归类题）

| 方法 | 特点 | 适用场景 |
|---|---|---|
| **访谈** | 一对一/一对多，深度高 | 用户少、需求复杂、涉密 |
| **问卷调查** | 覆盖面广，可统计 | 用户量大、分布广 |
| **观察 / 现场跟班** | 看真实工作流程，能发现用户"说不出来"的隐含需求 | 流程性强、用户表达困难 |
| **原型法** | 快速可视化，反复确认 | **需求模糊、用户说不清要什么** |
| **JRP / JAD（联合需求计划）** | 关键干系人集中开会，一次性敲定 | 跨部门、分歧大、需快速达成共识 |
| **头脑风暴** | 发散收集创意 | 方案探索阶段 |
| **德尔菲法** | 专家匿名多轮反馈，避免权威主导 | **专家预测、风险评估** |
| **文档分析 / 竞品分析** | 从现有资料与同类系统提炼 | 系统改造、升级项目 |

### 1.3 需求分析方法：结构化 vs 面向对象

| 维度 | 结构化分析（SA） | 面向对象分析（OOA） |
|---|---|---|
| 核心模型 | **DFD 数据流图** + 数据字典 + E-R 图 + 状态迁移图 | **用例模型** + 领域模型（类图）+ 交互模型 |
| 建模视角 | 功能与数据分离 | 对象封装了数据与行为 |
| 现状 | 传统方法，仍出现在案例题中 | 主流 |

### 1.4 DFD 数据流图（案例题常考"平衡原则"与"加工合法性"）

**四种基本元素**：外部实体（矩形/正方形）、**加工 / 处理**（圆角矩形或圆）、数据流（带箭头线段）、数据存储（开口矩形或两条平行线）。

**五条铁律（改错题得分点）**：

1. **加工必须有输入和输出**（"黑洞"：只有输入无输出；"奇迹"：只有输出无输入；"灰洞"：输入不足以产生输出）；
2. **数据流必须经过加工**——数据存储之间、外部实体之间、外部实体与数据存储之间**不能直接**有数据流；
3. **父图与子图必须保持数据流平衡**（进出父图某加工的数据流，与子图边界上的数据流数量和方向一致）；
4. **每个加工、每个数据流、每个数据存储都要有唯一名称**，数据存储不能重名冲突；
5. **数据流方向要合法**，标注清楚流向。

**分层结构**：顶层图（上下文图，只有一个加工代表整个系统，明确与外部实体的接口）→ 0 层图 → 1 层图 → ……

### 1.5 需求验证与确认

- **验证（Verification）**：需求规格说明书本身正确吗？——评审、走查、原型验证、测试用例反推。
- **确认（Validation）**：做的东西是用户真正要的吗？——用户签字确认、验收测试。
- **质量特性**：正确性、完整性、一致性、**无二义性**、可验证、**可追溯**、可行性、必要性、可修改性。

### 1.6 需求变更控制（案例大题稳定考点）

**标准流程（七步，必须能默写）**：

```
① 变更申请（书面提交，记录来源与内容）
② 变更评估（影响分析：范围 / 进度 / 成本 / 质量 / 风险 / 配置）
③ CCB 变更控制委员会审批（含用户、开发、测试、配置管理代表）
④ 变更决策通知干系人（无论批准与否都要回执）
⑤ 实施变更（修改需求基线及相关工作产品）
⑥ 验证变更（测试 + 评审，确认未引入新问题）
⑦ 配置更新与发布（更新需求跟踪矩阵、版本与基线，通知全体干系人）
```

**配套机制**：

- **需求基线**：经正式评审并批准的需求规格说明书，是变更的起点；
- **需求跟踪矩阵 RTM**：**正向跟踪**（需求 → 设计 → 代码 → 测试用例，确认都实现了）、**反向跟踪**（工作产品 → 需求，防止"镀金"）；
- **需求状态**：已建议 → 已批准 → 已实现 → 已验证 → 已交付（另有"已删除/已拒绝"）；
- **紧急变更**：可走快速通道事后补审批，但**必须记录**。

> **案例题破题套路**：题干出现"需求频繁变更、口头提要求、改完没人记录、上线发现漏做"，一律从**变更控制流程缺失 + 无需求基线 + 无 RTM + 用户参与不足**四个角度切入，逐条给可执行动作。

## 二、UML 总览

### 2.1 UML 2.x 的 14 种图

| 分类 | 图 | 核心用途 |
|---|---|---|
| **结构图（静态）** | **类图**、对象图、**包图**、**组件图**、**部署图**、复合结构图、制品图 | 刻画系统"是什么" |
| **行为图（动态）** | **用例图**、**活动图**、**状态机图**、**顺序图**、通信图、定时图、交互概览图 | 刻画系统"怎么做、怎么变" |

**交互图四兄弟**：

- **顺序图**：强调**消息的时间顺序**（案例题最爱考）；
- **通信图（协作图）**：强调**对象之间的结构关系与链路**，同一交互的另一种视图，可互相转换；
- **定时图**：强调**时间约束**（如超时、持续时间），生命线横向排列，状态沿时间轴变化；
- **交互概览图**：活动图 + 交互图的混合，用活动图框架组织多个交互。

## 三、用例图（必考）

### 3.1 基本元素

**参与者（Actor）**：系统**外部**与系统交互的人、组织或**其他系统**；用小人表示。**区分业务参与者与系统参与者**；主参与者（主动发起）与辅助参与者（被动响应，如支付系统）。

**用例（Use Case）**：系统为参与者提供的**完整价值单元**（一个可观测的结果），椭圆表示。**用例是需求，不是功能分解**——避免把用例画成"增、删、改、查"四个碎用例。

### 3.2 三种关系（最高频，必考）

| 关系 | 符号 | 语义 | 箭头方向 | 执行必然性 |
|---|---|---|---|---|
| **包含 include** | `<<include>>` 虚线箭头 | 多个用例**公共的、必须的**行为被抽取成被包含用例 | 从**基础用例**指向**被包含用例** | **一定执行** |
| **扩展 extend** | `<<extend>>` 虚线箭头 | 在**特定条件/扩展点**下才插入的**可选**附加行为 | 从**扩展用例**指向**基础用例**（方向相反！） | **条件触发才执行** |
| **泛化 generalization** | 实线空心三角箭头 | 子用例/子参与者继承父用例，可替换父出现 | 从**子**指向**父** | — |

**记忆口诀**：

- **include = 必须抽共用（"包含进来必须用"），箭头基础指向被包含**；
- **extend = 可选加特例（"条件满足才扩展"），箭头扩展指向基础**；
- 一句判断法：**把被包含/扩展的行为删掉，基础用例是否还完整？** 不完整 → include；仍完整 → extend。

**典型命题**：
- "用户登录" 与 "查询订单" → `<<include>>`（必须先登录，删除后不完整）；
- "查询订单" 与 "打印订单" / "导出 Excel" → `<<extend>>`（可选动作，删除后查询仍成立）；
- "支付" 与 "微信支付" / "银行卡支付" → **泛化**；
- 若把 include 箭头画反、或把 extend 画成 include → 案例题直接扣分点。

### 3.3 用例描述（规格说明，案例题可能要求补写）

基本流（主成功场景）+ 扩展流（异常与分支）+ 前置条件 + 后置条件 + 特殊需求 + 业务规则。

## 四、类图与对象图（必考）

### 4.1 六种关系（按由弱到强排序，必背）

| 关系 | 表示法 | 语义 | 生命周期 |
|---|---|---|---|
| **依赖 Dependency** | 虚线开放箭头 `---->` | 一个类的变化影响另一个（方法参数、局部变量、静态调用），临时性 | 临时 |
| **关联 Association** | 实线（可带箭头表示导航性） | 长期持有对方的引用，可标注**角色名**与**多重度** | 长期 |
| **聚合 Aggregation** | 空心菱形 + 实线 | **整体-部分**，部分**可脱离整体独立存在** | 松散 |
| **组合 Composition** | **实心菱形** + 实线 | **整体-部分**，部分与整体**同生共死** | 强 |
| **泛化 Generalization** | 实线 + 空心三角箭头，指向父类 | is-a 继承 | — |
| **实现 Realization** | 虚线 + 空心三角箭头，指向接口 | 类实现接口 | — |

**强弱顺序**：**依赖 < 关联 < 聚合 < 组合 < 泛化/实现**

**经典辨析（选择题常考）**：

- 汽车 — 轮胎：**聚合**（轮胎拆下来还能装别的车）；
- 人 — 心脏、公司 — 部门、订单 — 订单项：**组合**（部分不能脱离整体）；
- 学生 — 课程：关联（带多重度 `*` 对 `*`）；
- 鸟 — 企鹅：泛化。

### 4.2 多重度（Multiplicity）

| 写法 | 含义 |
|---|---|
| `1` | 恰好一个 |
| `0..1` | 0 或 1 个（可选） |
| `*` 或 `0..*` | 0 个或多个 |
| `1..*` | 1 个或多个 |
| `3..5` | 3 到 5 个 |

**注意方向**：多重度写在**关系另一端**，表示"本端的一个对象对应对端几个对象"。

### 4.3 类图的补充元素

- 类名、属性（`可见性 名称:类型 = 默认值`）、方法（`可见性 名称(参数):返回类型`）；
- 可见性：`+` public、`-` private、`#` protected、`~` package；
- 抽象类/抽象方法用**斜体**，`{abstract}` 约束；接口用 `<<interface>>` 或棒棒糖表示；
- 约束 `{readonly}`、注释（折角矩形 + 虚线连接）。

## 五、顺序图（交互建模，案例题最高频）

### 5.1 基本元素

| 元素 | 表示 | 说明 |
|---|---|---|
| 对象 | 顶部矩形，`:类名` 或 `对象名:类名` | 生命线由此向下延伸 |
| **生命线** | 垂直虚线 | 对象在某段时间内的存在 |
| **激活（控制焦点）** | 生命线上的窄长矩形 | 对象正在执行操作的时段 |
| 销毁 | 生命线末端的 `×` | 对象生命周期结束 |
| 创建 | 消息箭头直接指向对象矩形 | 可标 `<<create>>` |

### 5.2 消息类型（务必区分箭头形状）

| 类型 | 表示 | 语义 |
|---|---|---|
| **同步消息** | **实心三角箭头** | 发送者阻塞等待返回（方法调用） |
| **异步消息** | **开放箭头（线型箭头）** | 发送后立即继续，不等待 |
| **返回消息** | **虚线开放箭头** | 返回值 |
| 自消息 | 箭头指回自身生命线 | 对象内部调用 |
| 发现消息 | 起点为实心圆 | 来源不明 |

### 5.3 组合片段（Combined Fragment，案例题填图重点）

| 片段 | 含义 | 类比 |
|---|---|---|
| **alt** | 多选一分支，带监护条件 | if / else if |
| **opt** | 可选执行，带监护条件 | if |
| **loop** | 循环，可带次数 `[1..n]` | for / while |
| **par** | 并行执行 | 并发 |
| **break** | 条件满足则中断所在交互 | break |
| **critical** | 临界区，原子不可打断 | 事务 |
| **ref** | 引用另一张交互图 | 子图调用 |
| neg / assert | 无效交互 / 断言必须发生 | — |

### 5.4 顺序图 vs 通信图

| 顺序图 | 通信图 |
|---|---|
| 强调**时间顺序**，有明确时间轴 | 强调**对象间的结构关系（链路）** |
| 有生命线与激活框 | 无生命线，用链（实线）连接对象 |
| 适合分析流程时序 | 适合看清楚哪些对象有关联 |
| 可标注消息序号（常用于通信图） | 用**分层编号**（1、1.1、1.2、2）表示顺序 |

## 六、状态机图（状态图）

### 6.1 基本元素

- **初态**：实心圆，**有且仅有一个**；
- **终态**：空心圆内套实心圆，**可以有多个，也可以没有**；
- **状态**：圆角矩形，可含三个分区——状态名、**内部活动**（`entry` 进入动作 / `do` 持续活动 / `exit` 退出动作）、内部迁移；
- **迁移**：箭头，标注格式为 `事件 [监护条件] / 动作`；
- **自迁移**：回到自身状态；
- **复合状态**：内部包含子状态机；
- **历史状态**：`H`（浅历史，记住最近一层子状态）/ `H*`（深历史，记住全部嵌套层）；
- **并发区域**：复合状态内的分区，用虚线分隔，同时执行多个子状态机。

### 6.2 常考场景

订单状态（待支付 → 已支付 → 已发货 → 已签收 / 已取消）、设备状态、审批流状态。**案例题常要求补全状态名或迁移条件**。

### 6.3 状态图 vs 活动图（选择题高频辨析）

| 状态机图 | 活动图 |
|---|---|
| 关注**一个对象**在其生命周期内的状态变化 | 关注**活动之间的流程控制**（可跨多个对象） |
| 强调"**事件驱动**"，状态被动等待事件触发 | 强调"**活动驱动**"，动作完成后自动流转 |
| 适合描述单个对象的行为 | 适合描述业务流程、算法流程、并发 |

---

## 七、活动图

### 7.1 基本元素

起点（实心圆）、终点（同心圆）、**活动/动作**（圆角矩形）、**判断/合并**（菱形）、**分叉/汇合**（**粗水平线**，表示并发的**分叉 Fork** 与**汇合 Join**，必须配对出现）、**泳道 Swimlane**（纵向划分，按角色/部门/系统区分职责）、对象流（虚线箭头，连接活动与数据对象）、信号发送/接收（凸/凹五边形）。

### 7.2 与流程图的区别

| 活动图 | 传统流程图 |
|---|---|
| 支持**并发**（分叉/汇合） | 只有单线顺序与分支 |
| 支持**泳道**，能表达职责归属 | 无 |
| 支持**对象流**，能表达数据流动 | 无 |
| 属于 UML 面向对象模型，强调**对象行为** | 面向过程 |

## 八、组件图与部署图

### 8.1 组件图

- **组件**：矩形右上角带两个小矩形（或 `<<component>>`）；
- **接口**：**提供接口**（棒棒糖 lollipop，圆球 + 直线）与**需求接口**（插座 socket，半圆）；
- **端口 Port**：组件边界上的小方块，用于封装内部与外界的交互点；
- **连接器**：组件间通过接口的"装配"关系。

### 8.2 部署图

- **节点**：立方体，分为 **设备**（`<<device>>`，如服务器、交换机、PC）与**执行环境**（`<<execution environment>>`，如 JVM、Docker、Web 容器）；
- **制品 Artifact**：`<<artifact>>`，部署到节点上的物理文件（jar、war、dll、配置文件、数据库脚本）；
- **连接**：节点之间的通信路径，可标注协议（HTTP、JDBC、MQ）与带宽；
- 表达的是**运行时拓扑**，回答"软件跑在哪台机器的什么环境上"。

### 8.3 包图

包（`<<package>>`）用于组织模型元素，元素间有 **导入 import**（`<<import>>`，引入后可直接使用）与 **访问 access**（`<<access>>`，需限定名访问）关系，可表达**层次依赖、避免循环依赖**。

## 九、考法拆解与得分逻辑

### 9.1 综合知识（选择题）

**考法 1｜14 种图归类与选型**
题干给描述选图：
- "描述系统在时间维度上对象之间消息传递的顺序" → **顺序图**；
- "描述一个对象在其生命周期内所经历的状态" → **状态机图**；
- "描述业务流程并体现部门/角色职责划分" → **活动图（泳道）**；
- "描述软件在硬件节点上的物理部署" → **部署图**；
- "描述系统的功能需求与外部可见行为" → **用例图**；
- "强调对象间结构关系与链路" → **通信图**。

**考法 2｜include / extend 判断**（见 3.2，几乎每年必出）

**考法 3｜类图关系强弱与符号**
空心菱形 = 聚合；实心菱形 = 组合；虚线箭头 = 依赖；实线空心三角 = 泛化；虚线空心三角 = 实现。

**考法 4｜多重度与导航性**
"一名教师可指导多名学生，一名学生只能有一名导师" → 教师端 `1`，学生端 `*`。

**考法 5｜DFD 平衡原则与加工合法性**（见 1.4 五条铁律）

**考法 6｜需求层次归类**
"系统应在 3 秒内响应" → 非功能需求（性能）；"系统应提供订单查询功能" → 功能需求；"必须采用国产数据库" → 设计约束。

### 9.2 案例分析（主观题）

**题型 A：补充缺失元素**

答题顺序建议：**先整体读懂业务语义 → 再定位图形规范空缺 → 用规范术语作答**。

常见空缺类型：
1. 用例图：漏画参与者（尤其是**外部系统**这类参与者）、漏画 include（登录、支付这类公共前置）、extend 方向画反；
2. 类图：多重度缺失、聚合/组合用错、导航性缺失；
3. 顺序图：漏画**返回消息**、激活条位置错、对象命名缺冒号（应为 `对象名:类名`）、缺 alt/opt 条件。

**题型 B：指出并改正错误**

作答格式（每条一行，便于阅卷采分）：
> **错误 N**：图中 X 处 Y 关系画反了。
> **正确做法**：应改为 Z，理由是……（引用题干业务事实）

**题型 C：解释关系语义**

问"说明 include 与 extend 的区别"，必须答到三点：**必然性（必须 vs 条件可选）**、**箭头方向**、**抽离目的（复用公共行为 vs 隔离可选变化）**，并结合题干举例，否则拿不全分。

**题型 D：需求问题诊断（治理类大题）**

> ① **引用题干事实**："题干中用户频繁口头提出新需求，开发方直接修改代码，上线后才发现部分需求未实现……"
> ② **对应方法/原则**：缺少需求变更控制流程、未建立需求基线、缺少需求跟踪矩阵、需求评审与用户参与不足；
> ③ **可执行动作**：建立 CCB 与书面变更申请制度 → 建立需求基线并冻结 → 建立 RTM 做正向/反向跟踪 → 每次变更做影响分析并更新计划 → 变更后回归验证与配置发布 → 定期需求评审会，用户全程参与。

**主要失分点**：用口语化描述代替 UML 规范术语；只写"关系错了"不写正确做法与理由；include/extend 混用；把用例写成功能分解；需求题只谈技术不谈流程与机制。

### 9.3 论文素材（需求工程方向）

- **背景段**：某 XX 系统建设项目，涉及 N 个业务部门、M 类用户角色，需求差异大且随业务快速变化；
- **难点段**：需求获取阶段，用户难以准确表达诉求，各部门诉求冲突；建设过程中需求变更频繁；缺少有效的需求跟踪手段，导致上线功能与原始诉求偏差；
- **方案段**：
  1. **需求获取**：访谈（关键用户）+ 现场跟班（观察真实流程）+ **原型法**（需求模糊处快速确认）+ **JRP 联合需求会议**（跨部门分歧一次性协调）；
  2. **需求建模**：用**用例模型**刻画功能需求与系统边界，用**领域类图**建立统一业务概念，用**顺序图**澄清关键业务流程的时序，用**状态机图**描述核心业务对象（如订单）的状态流转；
  3. **需求管理**：建立需求基线 + **RTM 需求跟踪矩阵** + CCB 变更控制流程 + 影响分析模板 + 配置管理与版本控制；
  4. **需求验证**：分层评审 + 基于用例编写验收测试用例；
- **结果段**：需求评审一次通过率提升，变更从"口头随意改"变为"评估后有序纳入"，上线验收无重大功能缺失，返工率显著下降。

## 十、五分钟自测

1. "查询订单" 与 "打印订单" 是什么关系？（答案：`<<extend>>`，可选）
2. "查询订单" 与 "用户登录" 是什么关系？（答案：`<<include>>`，必须）
3. extend 的箭头从谁指向谁？（答案：**从扩展用例指向基础用例**）
4. 公司与部门之间是聚合还是组合？（答案：**组合**，实心菱形）
5. 汽车与轮胎之间是什么关系？（答案：**聚合**，部分可独立存在）
6. 顺序图中同步消息与异步消息的箭头区别？（答案：实心三角箭头 vs 开放箭头）
7. 状态图的初态有几个？终态可以有几个？（答案：初态**有且仅有一个**；终态可多个也可无）
8. 活动图中表示并发的是什么符号？（答案：**粗水平线**的分叉/汇合）
9. DFD 中"两个数据存储之间直接画一条数据流"是否正确？（答案：**错误**，数据流必须经过加工）
10. 需求变更控制的审批机构叫什么？（答案：**CCB 变更控制委员会**）
11. 需求跟踪矩阵中，"从测试用例反查到需求"属于正向还是反向跟踪？（答案：**反向跟踪**）
12. "系统响应时间 ≤ 3 秒"属于功能需求还是非功能需求？（答案：**非功能需求 / 性能需求**）

## 十一、速记口诀

- **include 必须抽共用、箭头基础指被包含；extend 可选加条件、箭头扩展指基础**；
- **依赖虚线、关联实线、聚合空心菱、组合实心菱；泛化实三角、实现虚三角**；
- **聚合能拆（轮胎），组合同命（心脏）**；
- **实心三角同步等，开放箭头异步走，虚线箭头是返回**；
- **alt 选一、opt 可选、loop 循环、par 并行、ref 引图**；
- **初态一个终态多，事件 [条件] / 动作**；
- **状态看一物、活动看流程；分叉汇合粗横线、泳道分责看得清**；
- **变更七步：申请—评估—审批—通知—实施—验证—发布**。
