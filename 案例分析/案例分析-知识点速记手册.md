## 一、分布式数据库

**一句话记忆：** 数据分布（适应组织）+ 局部自治（省通信）+ 冗余可靠（抗故障）+ 易扩充（好扩展）+ 好共享（可分担）。

**1. 相比集中式数据库的优点（5 点）**

1. 数据分布合理，适应分布式应用（物理分散、逻辑统一，避免长途传输）
2. 局部自治，响应快、通信开销小
3. 可靠性高、可用性好（多副本冗余，抗单点故障）
4. 可扩充性、灵活性好（按需增删结点，不受单机容量限制）
5. 数据共享性好，负载分散

**2. 分布透明性（三种，层次由高到低）**

| 透明性 | 含义 |
| --- | --- |
| 分片透明性（最高） | 用户只对**全局关系**操作，不必关心数据如何逻辑分片 |
| 位置透明性（次之） | 不必关心数据分片存储在哪个物理场地 |
| 局部数据模型透明性（最低） | 不必关心各场地采用何种数据模型（关系/网状）与局部模式 |

> 顺序不能颠倒：**分片 > 位置 > 局部数据模型**；透明层次越高，用户越简单、系统实现越复杂。

**3. 数据分片（四种方法 + 一致性）**

- **水平分片**：按**行**（元组）划分，如按地区拆订单表
- **垂直分片**：按**列**（属性）划分，需保留主键以便重构
- **混合分片**：水平 + 垂直结合
- **导出分片**：分片条件**由另一个关系的属性值决定**（最易被忽略）
- **全局一致性三要求**：全局数据的**一致性**、并发操作的**可串行性**、故障的**全局可恢复性**
- 分片正确性三准则：**完备性、可重构性、不相交性**

**易错点：** 导出分片最易漏；透明性顺序不能乱；冗余换来可靠，也引出一致性代价（与 CAP 呼应）。

## 二、软件开发方法：SDLC vs RAD

**一句话记忆：** **需求不清 + 系统复杂 + 工期紧**，是瀑布式 SDLC 的三个"死穴"。

**1. 放弃传统 SDLC 的原因**：需求不明确无法前期冻结、系统复杂需完整设计周期长、工期紧难按期交付、新技术难快速验证。

**2. RAD 基本思想**：以**用户为中心**、**原型驱动 + 迭代增量**、**工具与构件支撑**（可视化建模/可复用构件/代码生成）、**小团队强沟通**、**目标是快速交付**。核心是一个"快"字：快速原型、快速反馈、快速交付。

**3. 工具不熟 + 新 DBMS 的对策**：①外聘专家/骨干；②专项培训 + 厂商技术支持；③选成熟、文档全、兼容好的工具与构件、尽量复用；④先小原型试点再推广。

**SDLC vs RAD 对比**

| 维度 | SDLC（瀑布） | RAD |
| --- | --- | --- |
| 需求前提 | 前期须明确并冻结 | 可不明确，边做边明确 |
| 开发方式 | 阶段串行、线性 | 原型迭代、增量交付 |
| 用户参与 | 主要在需求阶段 | 全程深度参与 |
| 周期 / 文档 | 长 / 重 | 短 / 相对轻 |
| 适用场景 | 需求明确稳定 | 需求模糊、工期紧、用户可深度参与 |

**易错点：** RAD 不是"不要文档/不要设计"，而是**做轻做快**；RAD 的前提是**用户能深度参与**。

## 三、微服务架构

**一句话记忆：** **独立部署 + 故障隔离 + 团队自治 + 技术异构**（一病一药，对症单体四痛点）。

**1. 微服务优点（对应"单体病"）**

| 单体痛点 | 微服务优点 |
| --- | --- |
| 改一处要整体重部署 | 独立部署、独立上线 |
| 单模块拖垮全局 | 故障隔离、可用性高 |
| 多团队共用代码冲突多 | 团队自治、并行开发 |
| 技术栈被绑死 | 技术异构、选型灵活 |

（加分点：按需独立扩展/弹性伸缩、高内聚低耦合）

**2. 核心组件（口诀）**

- **API 网关 = 入口 + 鉴权 + 限流**：统一入口与路由转发、统一鉴权与安全管控、流量治理（限流/熔断/降级）与负载均衡。
- **服务注册与发现 = 注册 + 发现 + 健康检查**：实例启动登记地址；消费者查询/订阅实例列表；定期探测健康、上下线通知。

**3. 试运行三问题 → 三类治理组件**

| 问题 | 治理手段 | 常用组件 |
| --- | --- | --- |
| 跨服务数据不一致 | 分布式事务 / 最终一致性 | Seata、可靠消息、Saga / TCC |
| 日志分散难排查 | 集中式日志 | ELK / EFK、Loki |
| 调用链长难定位 | 分布式链路追踪（traceId + span） | SkyWalking、Zipkin、Jaeger |

**易错点：** 优点要**结合案例逐条对应**；**注册发现 ≠ 配置中心**；**API 网关 ≠ 路由器/防火墙**；问题3 要"一问题一方案"并点出**具体组件名**。

## 四、湖仓一体与流批一体

**一句话记忆：** **湖的灵活 + 仓的能力，一体存储、一体管理、免搬运**。

**1. 湖仓一体定义**：在**同一套架构**上融合数据湖（低成本、多格式、存算分离、存全量原始异构数据）与数据仓库（事务 ACID、Schema 管理、高性能查询、数据治理），通过**开放表格式**（Iceberg / Hudi / Delta Lake）叠加仓的能力，实现"一份数据存储、多种引擎按需分析、免搬运"。

**2. 三大核心优势（须写对比句）**

1. 支持异构数据统一存储与分析（传统数仓仅结构化）
2. 存算分离、弹性扩展、成本更低（传统数仓存算耦合、扩容贵）
3. 一份数据免搬运、链路更短、时效更高（传统须 湖→仓 ETL 搬迁）

**3. 四大治理问题 → 对应能力**

| 问题 | 治理能力 |
| --- | --- |
| 权限粗放 | 分层分域 + 库/表/行/列级细粒度授权 + RBAC/ABAC + 脱敏加密 + 审计留痕 |
| 流批口径不一致 | Flink 流批一体 + 统一 SQL/口径 |
| 数据质量无保障 | DQC 数据质量平台（规则 + 校验 + 拦截隔离 + 告警闭环） |
| 血缘缺失难溯源 | 元数据管理 + 数据血缘（溯源 / 影响分析） |

**4. 流批一体核心设计思想**：**一套引擎、一套代码（SQL）、一份数据、一个口径、一种语义**——流与批本质统一、统一存储与数据源、统一计算逻辑与口径、统一时间语义与容错（Watermark + Checkpoint + Exactly-Once）、架构 Kappa 化。

**5. 元数据 & 数据血缘**

- **元数据管理（数据治理的"大脑"）**：管技术/业务/管理三类元数据；作用是数据发现与目录、统一口径标准、挂载权限质量血缘、管理生命周期。
- **数据血缘（数据流转的"导航图"）**：记录表级/字段级全链路流转；作用是**故障溯源、影响分析、质量定责、合规审计、链路优化**。
- 关系：元数据是血缘的**载体与基础**，血缘是元数据的**动态关系体现**；一个管**静态描述**，一个管**动态关系**。

**Lambda vs 流批一体**：Lambda 是"流批两条链路、两套代码、两份数据、易不一致"；流批一体是"一条链路、一套代码、一份数据、一个口径、运维成本低"。

**易错点：** 湖仓一体 ≠ 两个系统简单叠加；必须写"对比句"；问题3 两小问都要答满。

## 五、嵌入式实时系统（RTSAD：DFD / STD）

**一句话记忆：** 环境模型管"对外交互"、行为模型管"因何事件变何状态"、耦合看"模块之间"、内聚看"模块内部"；总原则——**高内聚、低耦合**。

**1. 四个概念**

| 概念 | 描述对象 | 含义 | 优劣 | 工具 |
| --- | --- | --- | --- | --- |
| 环境模型 | 系统 ↔ 外部环境 | 与外部环境的数据交互、系统边界 | — | 数据流图 DFD |
| 行为模型 | 系统自身随时间的行为 | 状态、触发事件、响应动作 | — | 状态转换图 STD |
| 耦合 | **模块之间** | 相互依赖紧密度 | **越弱越好** | 模块结构图 |
| 内聚 | **模块内部** | 内部元素结合紧密度 | **越强越好** | 模块结构图 |

**2. 状态转换图（STD）三要素**：**状态**（方框）、**触发事件**（箭头标注）、**转换**（箭头）。自环表示状态不变但执行动作；STD 与**状态转换表**等价可互转。

**3. 数据流程图（DFD）**：四要素为**外部实体、加工（进程）、数据存储、数据流**；实时系统 DFD 扩展了**控制流（虚线）与控制加工**。

**4. 三类模型分工**：环境图（0 层 DFD，界定输入/输出）→ 数据流程图（分层 DFD，细化加工）→ 状态转换图（事件驱动的状态变迁）。

**易错点：** "结束程序"（T3，运行→终止，人主动）≠ "处理程序已结束"（T4，手动→终止，程序运行完毕）；(5) 已挂起→运行（恢复 T6）与 (6) 运行→已挂起（停止 T5）方向相反；填空填**事件编号**不填状态名；DFD 加工名用**动词短语**不能用状态名。

## 六、人工智能大模型系统架构

**一句话记忆：** **架构（Transformer）+ 上下文（窗口）+ 推理加速（KV 缓存）+ 向量（Embedding）+ 检索增强（RAG）**；凡带"校验/认证/加密/合约/数据表"字样的一律排除。

**1. 大模型核心技术（本题命中 5 项）**

| 技术 | 定位 |
| --- | --- |
| Transformer 架构 | 底层网络结构，自注意力机制 |
| 上下文窗口机制 | 决定单次可处理 token 长度 |
| KV 缓存推理加速 | 缓存历史 K/V，加速自回归生成 |
| 向量嵌入 Embedding | 文本→语义向量，检索与相似度基础 |
| RAG 检索增强生成 | 检索外部知识 + 生成，减少幻觉、可溯源 |
| （微调 Fine-tuning） | 领域数据继续训练（本题未列入，勿多选） |

**2. 归一化激活函数**：答案是 **Softmax**，作用是**概率归一化、输出最优生成 token**。注意区分：ReLU/Sigmoid 是其他激活函数（防梯度消失属**训练阶段**），D/E/F/H/J/K 是密码学干扰项。

**3. 大模型推理全流程（一条主线）**

> 用户输入 →（**安全脱敏清洗**）→ 向量嵌入 Embedding →（**向量库检索 / RAG**）→ 拼接上下文 +（**历史 KV 缓存**）→ **模型推理生成 token** →（**内容安全过滤**）→ 合规输出。

四项管控机制落点：安全脱敏（输入侧）、向量库检索（RAG）、KV 缓存（推理加速）、token 计数管控（输出侧）。

**易错点：** 题1 只看题干【说明】点名的五类技术；选项上限 5 个、**多选不得分**；区分输入侧安全（脱敏）与输出侧安全（内容过滤）。

## 七、Web 应用与 AI 智能体融合平台

**一句话记忆：** 微服务强在**并发隔离、分布式调度、安全管控、弹性扩展**；一体化架构弱在**并发上限、安全治理、横向扩展**。

**1. 后端架构选型对比**

| 维度 | 微服务（Spring Cloud） | 一体化（FastAPI+Node.js） |
| --- | --- | --- |
| 并发 | 高并发、流量隔离、异步非阻塞 | 轻量启动快，中低并发，单实例差，需多实例集群 |
| 智能体调度 | 分布式调度、多智能体协同、弹性扩缩容、任务编排 | 单实例轻量调度，适合少量智能体 |
| 安全管控 | 认证、限流、审计、行为风控完善 | 仅简单认证鉴权，需自行集成安全组件 |
| 扩展性 | 服务独立部署、横向扩展、故障隔离 | 横向扩展弱、大规模集群管理复杂 |
| 适用 | 大规模、强治理、生产级 | 原型验证、中小规模、快速上线 |

**2. 负载均衡技术（口诀）**：**DNS 粗 → 四层快 → 七层灵活 → 推理智能 → 哈希粘性**。

| 技术 | 产品 | 优势 | 劣势 |
| --- | --- | --- | --- |
| DNS | 轮询、GSLB | 简单、就近接入 | 粒度粗、不感知健康与负载 |
| 四层 | LVS、F5、Nginx stream | 吞吐高、时延低 | 只认 IP/端口，不能按内容路由 |
| 七层 | Nginx、HAProxy、Envoy、Kong | 按 URL/Header 路由、灰度/限流/会话保持 | 性能较低、配置复杂 |
| 推理感知调度 | K8s+KServe、vLLM/TGI、Ray Serve | 按队列/显存/token 负载分发、支持流式 | 实现复杂、耦合推理框架 |
| 一致性哈希 | Nginx、Envoy、Redis Cluster | 会话/上下文粘性、缓存命中高 | 易热点、需再平衡 |

算法策略：轮询、加权轮询、随机、最少连接、最短响应、一致性哈希（后两者适合长耗时、负载不均的推理）。

**3. 常用中间件（口诀：入口→解耦→加速→治理→检索→观测→安全）**

| 类别 | 作用 | 典型产品 |
| --- | --- | --- |
| 反向代理/负载均衡/网关 | 高可用入口、流量分发、限流鉴权 | Nginx、HAProxy、Envoy、Kong、Spring Cloud Gateway |
| 消息队列 | 异步解耦、削峰填谷、任务通信 | Kafka、RabbitMQ、RocketMQ、Pulsar |
| 缓存 | 加速、会话/上下文存储 | Redis、Memcached |
| 注册与配置中心/分布式协调 | 服务发现、扩缩容、配置管理 | Nacos、Consul、Eureka、ZooKeeper、etcd |
| RPC/服务通信 | 智能体/微服务间调用 | gRPC、Dubbo、OpenFeign |
| 向量数据库/检索引擎 | 知识库检索、RAG 召回 | Milvus、Qdrant、Chroma、Elasticsearch、PGVector |
| 容器编排/调度 | 动态扩缩容与资源调度 | Kubernetes、Docker、KubeSphere |
| 任务调度/工作流 | 任务执行、多智能体协同编排 | Airflow、Celery、Temporal、XXL-Job |
| 日志监控链路追踪 | 观测、故障定位、行为审计 | ELK/EFK、Prometheus+Grafana、SkyWalking、Jaeger |
| 认证授权/安全 | 数据安全、统一身份、行为风控 | Keycloak、OAuth2/JWT、Vault |

**易错点：** 填空要"维度对应、优劣对称"；负载均衡要答**负载感知调度 + 四层/七层组合**；**消息队列（解耦）≠ 缓存（加速）**；**向量数据库**是新增得分点。

## 八、Web 应用（LLM 智能问答端到端交互流程）

**一句话记忆：** **前端鉴权脱敏 → 网关路由限流 → 应用检索组装（RAG）→ 模型推理生成（可流式）→ 后处理审核 → 网关流式返回**。

**流程六段（顺题干主线"前端 → API 网关 → 模型推理 → 结果返回"）**

| 阶段 | 模块 | 关键动作 |
| --- | --- | --- |
| ① 发起 | 小程序/移动端 | 登录鉴权、输入校验、敏感脱敏，HTTPS 请求 |
| ② 入口 | **API 网关** | 路由转发、限流、鉴权、身份透传 |
| ③ 应用层 | 应用服务 | 解析问题、查缓存、**向量库检索做 RAG**、组装提示词与上下文 |
| ④ 推理层 | 模型服务网关 → **推理服务** | 分词/嵌入、Prompt 组装、**LLM 生成**（必要时先 OCR）、流式输出 |
| ⑤ 后处理 | 推理服务 → 应用层 | 结果校验、内容安全审核、格式化、引用来源封装 |
| ⑥ 返回 | 应用层 → 网关 → 前端 | 写库、审计日志，**SSE/WebSocket 流式推送** |

**易错点：** 必须点出 **API 网关、模型推理服务、流式返回**三类核心模块；易漏 **RAG/向量库、模型服务网关、SSE/WebSocket、内容安全审核**；只考**在线推理链路**，不涉及模型训练。

## 九、嵌入式多核程序设计

**一句话记忆：** **并发 = 交替执行（单核可实现，逻辑同时）；并行 = 真正同时（须多核，物理同时）**。

**并发 vs 并行**

| 维度 | 并发 | 并行 |
| --- | --- | --- |
| 核心含义 | 同时存在、交替使用 CPU | 同时执行 |
| 时间视角 | 宏观同时、**微观串行** | 宏观微观都同时 |
| 硬件要求 | 单核即可（时间片轮转） | 必须多核 |
| 本质 | 逻辑上"同时" | 物理上"同时" |
| 目的 | 提高响应能力与资源利用率 | 缩短计算时间、提高吞吐 |

> 比喻：停下吃饭去接电话=并发；边吃饭边打电话=并行。

**记忆轴：单核 vs 多核**

- **延迟隐藏**是**单核**多线程的动机（判"多核为延迟隐藏"→ 错）；多核多线程目标是**并行、缩短计算时间**。
- **伪共享**只在**多核**存在（旋转 Cache 一致性），说"单核也有"→ 错。
- 单核的简化假设（"同一时刻只有一个线程真正运行"）**不适用于**多核（→ 错）；单核优化代码在多核会不稳定（优先级反转）→ 对。
- 多核要高性能够用，**必须多线程 + 均衡分配负载到各核**。

**易错点：** 并发≠并行（判据：是否同一时刻真正同时执行）；不要被"只有…才能""就是…"的绝对措辞带偏，要按知识本身判断。

## 十、UML 用例建模（需求分析）

**一句话记忆：** 参与者 = **两类用户 + 管理人员 + 支付系统**；用例 = **进、出、异常、统计**四件事。

**1. 识别参与者与用例**

- **参与者**：只指**人**和**与本系统交互的外部系统**（月卡用户、临时用户、停车场管理人员、第三方支付系统）。车牌摄像机、车位传感器是**系统内部采集部件，不是参与者**。
- **用例**（须对参与者有可观察结果）：入场管理、出场管理（含计费缴费）、异常处理、数据统计。

**2. 顺序图 vs 协作图（交互图）**

| 维度 | 顺序图（序列图） | 协作图（通信图） |
| --- | --- | --- |
| 侧重点 | **时间顺序** | **对象间结构/链接关系** |
| 表现 | 纵向时间轴，消息自上而下 | 无时间轴，拓扑摆放 |
| 顺序表达 | 位置（上下） | 消息**编号** |
| 关系 | **语义等价、可相互转换** | 同左 |

**顺序图 4 种核心元素**：**对象**（谁）→ **生命线**（垂直虚线，存在时段）→ **激活**（矩形条，正在执行）→ **消息**（彼此通信）。

**3. 构建用例模型步骤**：**定边界 → 找参与者 → 找用例 → 理关系 → 画图 → 写规约 → 评审**。
（确定系统边界 → 识别参与者 → 识别用例 → 明确 use case 关系 include/extend/泛化 → 绘制用例图 → 编写用例规约 → 评审确认）

**易错点：** 参与者 ≠ 系统内部模块；用例必须"对参与者有可观察结果"（"查询数据库""计算费用"是用例内部活动）；顺序图/协作图**语义等价**，只是侧重点不同；四元素别漏**激活**。

## 十一、面向对象分析与设计

**一句话记忆（分析步骤）：** **理需求 → 画用例图 → 画类图 → 画动态图 → 评审迭代**（从需求到静态结构再到动态行为）。

**1. 建立分析模型的主要步骤**

| 步骤 | 产出 |
| --- | --- |
| ① 需求分析 | 需求规格（功能 + 非功能） |
| ② 建立用例模型 | 用例图（参与者、用例、关系） |
| ③ 建立类模型（静态） | 类图（类、属性、操作、类间关系） |
| ④ 建立动态模型 | 时序图、活动图、状态图 |
| ⑤ 模型验证与迭代 | 评审意见与完善后的模型 |

**2. UML 类的 4 种常见关系**

| 关系 | 含义 | 图示 | 本系统举例 |
| --- | --- | --- | --- |
| **关联** | 稳定的结构联系 | 实线（可标多重性 1:*） | 读者 — 预约单 |
| **聚合** | **弱**整体—部分（部分可独立存在） | **空心菱形**（指向整体） | 书房 — 座位 |
| **组合** | **强**整体—部分（同生共死） | **实心菱形**（指向整体） | 预约单 — 时段明细 |
| **泛化** | 一般—特殊（继承） | **空心三角**（指向父类） | 读者 — 学生/教师读者 |

> 标准四分法（UML 教科书）：依赖、关联、泛化、实现。

**3. 面向对象设计中的三种类（BCE）**

| 类型 | 定义 | 作用 | 示例 |
| --- | --- | --- | --- |
| **实体类** | 需持久保存的业务对象 | 承载业务数据与业务逻辑 | 读者、书房、预约单 |
| **边界类** | 系统与参与者交互的界面 | 负责输入输出、隔离内外 | 预约界面、核验终端、报表界面 |
| **控制类** | 用例的业务控制逻辑 | 协调边界类与实体类、完成用例流程 | 预约/核验/统计控制类 |

> 记忆：**实体类管"数据"、边界类管"界面"、控制类管"流程"**（MVC/BCE 的 E-B-C）。

**易错点：** 聚合 vs 组合判据是"**部分能否脱离整体独立存在**"（能→聚合空心菱形；不能→组合实心菱形），菱形**指向整体**、泛化三角**指向父类**；问题1 要成体系（不能只答"画用例图"）；问题3 别把"三种类"答成"三种设计模式/继承"；注意字数限制。
